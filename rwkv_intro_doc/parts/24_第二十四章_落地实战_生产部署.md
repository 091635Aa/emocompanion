# 第二十四章 落地实战：把 RWKV 部署到真实产品

前面我们学会了"跑起来"，这一章解决"跑得稳、跑得便宜、跑得专业"。无论你是给公司做私有化助手，还是把自己的 AI 陪伴应用上线，这章的工程实践清单都值得照抄。

## 24.1 从 Demo 到生产：差距在哪里

本地 `ollama run` 和真实产品之间，隔着一整套"工程问题"。先看清差距，再对症下药：

| 维度 | Demo（本地玩） | 生产（上线产品） |
| --- | --- | --- |
| 并发 | 1 个用户 | 几十上百并发 |
| 稳定性 | 崩了重开 | 需要监控、告警、自动恢复 |
| 成本 | 无所谓 | 必须核算 token 成本 / 硬件成本 |
| 安全 | 无要求 | 内容过滤、隐私合规、防注入 |
| 质量 | 聊天就行 | 需要评测、回退、A/B |
| 记忆 | 手动存状态 | 状态库、多用户隔离、持久化 |

**核心思路**：RWKV 最大的工程红利是"状态（State）"。Transformer 产品要缓存一整套 KV 历史才能续聊，RWKV 只需要持久化一份固定大小的状态文件——这会让你的存储和续聊逻辑简单一个数量级。

## 24.2 服务架构：单机 / 多机怎么选

根据你的 QPS（每秒请求数）和预算，有三种典型的服务形态：

![RWKV 生产部署架构](img/fig26_prod_arch.png)

**形态一：单机轻服务（个人/小团队）**

```bash
# 用 llama.cpp 起一个 OpenAI 兼容服务，几十个用户够用
./llama-server -m rwkv-7-g1-2.9B-Q4_K_M.gguf --port 8080 \
  --ctx-size 8192 --n-gpu-layers 99
```

- 优点：简单、零运维、成本极低；
- 适用：内网工具、个人 AI 助手、小流量陪伴应用。

**形态二：vLLM 高并发服务（对外产品）**

```bash
pip install vllm
python -m vllm.entrypoints.openai.api_server \
  --model /path/to/rwkv-7 \
  --port 8000 --max-model-len 8192
```

- 优点：连续批处理（continuous batching）吞吐高、OpenAI 兼容；
- 适用：面向公众的聊天产品、多租户 SaaS。

**形态三：混合架构（大模型 + 小模型/规则）**

- 80% 简单请求走 RWKV 小模型（1.5B/2.9B 量化），省成本；
- 20% 复杂请求路由到大模型，保证质量；
- 配一个**路由层**（按意图/关键词/长度判断走哪条路）。

## 24.3 状态管理：RWKV 的"杀手级工程实践"

这是 RWKV 相对 Transformer 最独特、最值得利用的工程点。核心模式是**"状态即身份"**：

![状态管理与多角色记忆](img/fig27_state_mgmt.png)

```python
from rwkv.model import RWKV
from rwkv.utils import PIPELINE

model = RWKV(model="/path/rwkv-7.pth", strategy="cuda fp16")
pipe = PIPELINE(model, "rwkv_vocab_v20230424")

def new_session(role_id):
    """每个角色/用户一个独立状态"""
    return {"role": role_id, "state": None, "history": []}

def chat(sess, text):
    out, sess["state"] = model.run([text], sess["state"])  # 传旧状态、收新状态
    sess["history"].append(text)
    return out
```

**生产落地的三个要点：**

1. **状态持久化到数据库**：把 `state` 序列化存进 Redis / 数据库，用户下次进来直接读回，实现"跨会话不失忆"——而 Transformer 想做同样的事，要存整段 KV Cache，代价大得多。
2. **多用户隔离**：每个用户一份状态，天然隔离，互不串台；这比"把所有上下文拼一起再丢给模型"干净得多。
3. **状态归档与分片**：一个角色一个文件/一个 key；长对话可用"总结压缩"定期把旧状态精简。

> **为什么这对你的产品重要**：AI 陪伴/情感智能体的核心卖点就是"它记得我"。用 RWKV，这个记忆是"一等公民"（一份文件的事），实现成本远低于 Transformer 路线。

## 24.4 性能与成本调优清单

按"投入产出比"排序，从最划算的开始：

| 手段 | 效果 | 成本 |
| --- | --- | --- |
| 量化（Q4_K_M / Q8_0） | 显存降 4–8 倍，速度提升 | 零成本，精度略降 |
| 选对模型规模 | 2.9B 换 7B，速度翻倍以上 | 视需求 |
| 开启 Albatross / 官方内核 | RWKV-7 提速明显 | 零成本 |
| vLLM 连续批处理 | 吞吐提升数倍 | 需要 GPU 服务 |
| 前缀/状态缓存 | 多轮请求避免重复计算 | 需自己实现 |
| 批处理 + 异步 | 客户端体验更稳 | 需要工程改造 |
| 小模型兜底路由 | 综合成本大幅下降 | 需要路由逻辑 |

**量化速查**（以 2.9B 为例，大致值）：

| 精度 | 显存占用 | 备注 |
| --- | --- | --- |
| fp16 | 约 6GB | 质量最好 |
| INT8 / Q8_0 | 约 3GB | 质量几乎无损 |
| Q4_K_M | 约 1.8GB | 性价比之王 |
| Q4_K_S | 约 1.6GB | 更小，质量略降 |

## 24.5 质量与体验：评测、监控、兜底

上线前请建立三条防线：

**① 评测集**：准备 50–100 条覆盖你业务场景的"黄金问题"，每次改模型/改参数后跑一遍，对比输出质量。别凭感觉上线。

**② 监控指标**：
- 延迟（首 token 延迟、平均 token/秒）；
- 错误率（超时、空回复、报错）；
- 成本（每日 token 消耗、GPU 利用率）；
- 业务指标（对话轮数、留存、好评率）。

**③ 兜底策略**：
- 超时自动重试一次；
- 空回复/报错时返回预设话术；
- 检测到敏感内容时走安全话术；
- 大模型挂了自动降级到小模型。

## 24.6 安全与合规：别踩的坑

| 风险 | 应对 |
| --- | --- |
| 提示词注入 | 严格角色设定 + 系统提示词隔离 + 输入过滤 |
| 有害内容 | 输出侧内容审核（关键词 + 分类器） |
| 隐私数据 | 模型私有化部署、日志脱敏、加密存储状态 |
| 版权/合规 | 确认 Apache 2.0 商用条款、注明生成内容 |
| 幻觉 | 关键事实类场景加 RAG 检索约束 |

