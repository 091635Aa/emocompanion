# 第二十七章 常见报错与排查手册

动手过程中，报错是常态，别慌。这一章把 RWKV 从部署到运行最常见的报错整理成"症状 → 原因 → 解法"的速查手册。遇到问题先来这里翻，能省下大量瞎折腾的时间。

## 27.1 通用排查方法论

在逐条查错之前，先记住一套"通用排查四步法"——它能解决八成问题：

1. **看完整报错**：报错最后几行才是关键（`Traceback` / `Error` 之后的正文）。别只看开头。
2. **搜一下**：把**报错原文**（英文部分）复制到搜索引擎 / rwkv.cn / Discord，十有八九有人踩过。
3. **缩小范围**：用"最小复现"测试——只跑最简命令，把环境、模型、代码变量逐个排除。
4. **看版本**：`rwkv` / `torch` / `llama.cpp` / `ollama` 版本不匹配是高频元凶，先统一版本。

**通用环境诊断命令：**

```bash
python -c "import torch; print(torch.__version__, torch.cuda.is_available())"
ollama list && ollama --version
nvidia-smi            # 看显存是否够
free -h               # 看内存是否够
```

## 27.2 安装与环境类报错

| 症状 | 常见原因 | 解法 |
| --- | --- | --- |
| `pip install rwkv` 报编译错误 | 缺编译工具 / 版本过旧 | `pip install --upgrade pip setuptools wheel`，再装 C++ 编译器 |
| 模型下载极慢或失败 | 国内网络访问 Hugging Face 慢 | `export HF_ENDPOINT=https://hf-mirror.com` 走国内镜像 |
| `ModuleNotFoundError: rwkv` | 装错环境 / 未激活虚拟环境 | 检查 `which python`，在 venv 里重新 `pip install` |
| `AttributeError: ... has no attribute ...` | 库版本太老 | `pip install -U rwkv rwkv_tokenizer` 升级到最新 |
| 加载 `.pth` 报 `unexpected key` | 模型文件不完整/损坏 | 重新 `huggingface-cli download`，校验文件大小 |

**镜像加速示例：**

```bash
export HF_ENDPOINT=https://hf-mirror.com
pip install rwkv -i https://pypi.tuna.tsinghua.edu.cn/simple
```

## 27.3 显存 / 内存类报错

| 症状 | 常见原因 | 解法 |
| --- | --- | --- |
| `CUDA out of memory` | 模型太大 / 上下文太长 / 并发太多 | 换量化版、缩短上下文、`strategy="cuda fp16"`、加 `--n-gpu-layers` 分层 |
| CPU 跑 `MemoryError` | 内存不够加载 fp16 | 下载 GGUF Q4/Q8 量化，用 llama.cpp 跑 |
| 加载即崩、进程被杀 | OOM 被系统 Kill | 用 `Q4_K_M` 量化版，先测 `free -h` |
| 显存占用随对话暴涨 | 用了非 RWKV 方案 / 上下文没限制 | RWKV 显存应恒定；检查是否误开了长上下文或缓存 |

**给 2.9B 模型的显存速查（约）：**

| 精度 | 显存 | 说明 |
| --- | --- | --- |
| fp16 | ~6GB | 质量最好 |
| Q8_0 / INT8 | ~3GB | 推荐平衡点 |
| Q4_K_M | ~1.8GB | 低显存首选 |

## 27.4 推理质量类"报错"（不算报错，但很常见）

| 症状 | 常见原因 | 解法 |
| --- | --- | --- |
| 回复"复读机" / 一直重复 | temperature 过低、无重复惩罚 | `temperature=0.9` + 开启重复惩罚 / `presence_penalty` |
| 中文乱码 / 输出怪字 | 用了错误 vocab 文件 | 用模型自带的 vocab（如 `rwkv_vocab_v20230424.txt`） |
| 回复过于简短/废话 | 模型偏小 + prompt 引导不足 | 调高 top_p、给更明确的指令、换更大模型 |
| 回答内容瞎编（幻觉） | 所有 LLM 通病 | 关键事实走 RAG 检索约束 |
| 长对话后半段变笨 | 状态被挤压 / 上下文太长 | 分段总结、定期压缩状态、用 RAG 分担 |

**采样参数速调口诀**：要**稳** → 低 temperature（0.2–0.5）；要**创意** → 高 temperature（0.8–1.1）；要**不重复** → 打开重复惩罚；要**准确** → 配 RAG。

## 27.5 服务与 API 类报错

| 症状 | 常见原因 | 解法 |
| --- | --- | --- |
| `Address already in use` | 端口被占用 | 换端口：`--port 8081`；或 `lsof -i:11434` 找占用进程 |
| `Connection refused` | 服务没启动 / 地址写错 | 确认服务在跑、host 与端口一致；跨机器用 `--host 0.0.0.0` |
| 前端请求被 CORS 拦截 | 浏览器跨域限制 | 后端加 CORS 中间件，允许你的前端域名 |
| API 返回 401 / 无响应 | 未带鉴权 / 模型名错误 | 检查 `Authorization` 头与 `model` 参数拼写 |
| vLLM 启动报 `model not found` | 路径/格式不对 | vLLM 需要 HF 目录结构或 Safetensors，确认格式 |

**Ollama 常见问题速查：**

```bash
ollama ps              # 看当前加载的模型和显存
ollama rm <model>      # 清理不要的模型
ollama run xxx --verbose   # 看耗时与 token 速度
```

## 27.6 微调与状态类报错

| 症状 | 常见原因 | 解法 |
| --- | --- | --- |
| LoRA 微调 `OOM` | batch 太大 / 序列太长 | 减小 `batch_size`、`micro_bsz`、`ctx_len`，或用 QLoRA |
| 加载 `.st` 状态报维度不匹配 | 模型版本/规模不一致 | 状态文件和模型必须同版本同规模，重新导出 |
| 微调后变傻 / 灾难性遗忘 | 学习率太高 / 步数过多 | 降学习率（如 1e-5）、用 LoRA 而非全参、加正则 |
| 状态文件读取为空 | 序列化/路径问题 | 检查 pickle 文件完整性，确认读的是同一路径 |

**State Tuning 的黄金法则**：状态文件是"记忆快照"，换模型权重前先导出 `.st`；它只负责"性格/记忆"，不负责"知识"——知识靠权重或 RAG。

排查优先级从高到低：**环境与版本 → 显存/内存 → 模型文件完整性 → 参数设置 → 代码逻辑**。90% 的问题都集中在"版本不匹配"和"显存不够"这两类上，先确认它们再深挖。
