# 第十二章 应用场景与工程套用：把它用到我们自己的 AI 陪伴项目

这是全书的"落地章"。前面讲清了 RWKV 是什么、强在哪，这一章回答最重要的问题：**在我们的"AI 陪伴 / 情感智能体"工程里，RWKV 能怎么用？怎么接？** 我们会给出整体架构、模块拆解、以及可直接落地的实现思路。

## 12.1 先看应用全景：RWKV 适合哪四类场景

![四类典型应用场景](img/fig21_app_us.png)

在动手之前，先建立"RWKV 擅长什么"的全局观：

### 12.1.1 场景一：长会话 / 角色扮演 / 陪伴对话（核心）

- 用户与 AI 长期、高频、多轮交流；
- 需要"越聊越懂你"，且希望成本可控；
- **RWKV 的恒定内存 + 状态持久化**正好命中痛点。

![长会话与状态持久化](img/fig19_app_chat.png)

### 12.1.2 场景二：RAG 知识问答 / 智能客服

- 要基于私有文档回答；
- 长上下文 + 自带句嵌入，让 RAG 又好又省。

### 12.1.3 场景三：边缘 / 低配设备部署

- 树莓派、旧笔记本、手机、离线场景；
- 8GB 内存都能跑，隐私数据不出本地。

![边缘设备部署](img/fig20_app_edge.png)

### 12.1.4 场景四：个性化微调 / 低成本定制

- 让模型"变成某个性格/人设"；
- State Tuning 让个性化几乎零成本。

## 12.2 我们的场景：AI 陪伴 / 情感智能体的痛点

假设我们正在做一个 **AI 陪伴 / 情感智能体产品**（比如"虚拟朋友、心理陪伴、角色扮演伙伴"）。它有几个非常典型的痛点：

| 痛点 | 具体表现 | Transformer 的困境 | RWKV 的解法 |
| --- | --- | --- | --- |
| 长会话成本高 | 用户每天聊几十轮，长期陪伴 | KV Cache 越聊越贵，最终爆内存 | 状态固定，聊多久都便宜 |
| 需要长期记忆 | 记住用户性格、过往、偏好 | 要么全喂历史（贵），要么自建记忆 | 原生状态可持久化，天然"记得" |
| 部署成本敏感 | C 端产品要控制硬件成本 | 显存要求高 | 8GB 都能跑，CPU 可跑 |
| 隐私合规 | 聊天内容敏感 | 上云有合规风险 | 本地/私有化部署更容易 |
| 个性化人设 | 不同用户要不同"性格" | 每个都要微调，贵 | State Tuning，几乎零成本换人设 |

**结论**：AI 陪伴 / 情感智能体，几乎就是为 RWKV 的优缺点量身定做的场景。

## 12.3 整体架构设计：一张图看懂

我们把产品拆成"用户层 → 智能体应用层 → 模型层 → 能力层"四层：

![套用我们场景的整体架构](img/fig21_app_us.png)

| 层级 | 组件 | 作用 |
| --- | --- | --- |
| 用户层 | App / 微信 / 网页 / 语音 | 用户入口 |
| 智能体应用层 | 角色人设挂载、情感状态追踪、长期记忆、注入控制 | 业务逻辑 |
| 模型层 | RWKV-7（本地/边缘部署） | 对话生成核心 |
| 能力层 | TTS 语音、多模态、向量库（RAG） | 扩展能力 |

### 12.3.1 模块拆解

1. **角色人设挂载**：用系统提示词或 State Tuning 设定"小暖"的性格；
2. **情感状态追踪**：记录用户当前情绪（高兴/难过/焦虑），动态调整回复风格；
3. **长期记忆（状态持久化）**：用 RWKV 的状态 S 存档用户的"人生故事"；
4. **注入控制**：按需注入 RAG 片段 / 情境 / 知识；
5. **TTS 语音**：把文字回复变成语音，提升陪伴感。

## 12.4 模块一：角色人设挂载（两种方式）

**方式 A：提示词（最快）**

```python
SYSTEM = """你叫小暖，是一个温柔耐心的 AI 伙伴。
你的说话风格：简短、温暖、先共情再建议。
你永远记得：用户需要的是被理解，而不是被说教。"""
```

**方式 B：State Tuning（更"入戏"）**

- 用 RWKV-PEFT 对"小暖"风格的对话做 State Tuning；
- 得到 `.st` 状态文件，推理时挂载；
- 好处：人设更稳定，不依赖每轮塞一大段提示词，也更省 token。

**工程建议**：先用提示词快速验证人设，稳定后转 State Tuning 固化，省成本、效果更好。

## 12.5 模块二：情感状态追踪

让 AI 不只是"会聊天"，还能"察觉情绪"：

```python
EMOTION_PROMPT = """
请分析用户这句话的情绪，只输出一个词：开心/平静/难过/焦虑/愤怒/疲惫。
用户说："{msg}"
"""

def detect_emotion(msg):
    r = chat(EMOTION_PROMPT.format(msg=msg))
    return r.strip().split()[0] if r else "平静"

# 根据情绪调整回复风格
def respond_with_emotion(user_id, msg):
    emo = detect_emotion(msg)
    if emo in ("难过", "焦虑", "疲惫"):
        sys = "用户现在情绪低落，请先充分共情，语气更温柔，避免说教和玩笑。"
    else:
        sys = "用户情绪不错，可以更轻松活泼一些。"
    return chat_with_system(user_id, sys, msg)
```

## 12.6 模块三：长期记忆 = 状态持久化

这是 RWKV 相对其他架构的"降维打击"：

```python
# 每个用户一个状态文件 = 一份"专属人生记忆"
def get_memory(user_id):
    return load_state(f"memory_{user_id}.pkl")

def remember(user_id, new_state):
    save_state(new_state, f"memory_{user_id}.pkl")

# 使用
state = get_memory(user_id)
reply, state = pipeline.generate(prompt, state=state)
remember(user_id, state)   # 记忆自动"续上"
```

**对比 Transformer 的做法**：Transformer 通常要把全部历史消息重新喂进去（token 成本随记忆长度爆炸），或引入外部向量记忆库做检索；RWKV 直接把"记忆"压缩在状态里，随聊随存，几乎零额外成本。

## 12.7 模块四：注入控制与多模态扩展

- **RAG 注入**：当用户问到产品、知识类问题时，检索知识库片段注入（见第十一章）；
- **情境注入**：比如白天/深夜、忙碌/闲暇，动态调整语气；
- **TTS 语音**：把回复文本交给 TTS（如 Edge-TTS、开源 TTS），输出语音；
- **多模态**：RWKV 官方支持多模态方向，未来可接入语音/视觉。

## 12.8 部署选型：我们的产品该用哪条路

结合产品阶段：

| 阶段 | 推荐部署 | 理由 |
| --- | --- | --- |
| Demo/原型 | Ollama 或 RWKV-Runner 本地跑 | 最快跑通，验证产品 |
| 内测（少量用户） | llama.cpp / Ollama + OpenAI 兼容 API | 低成本支撑几十个并发 |
| 正式（多用户） | vLLM 服务化 + 状态持久化层 | 高吞吐、可水平扩展 |
| 隐私敏感 | 本地/私有化部署 | 数据不出域，合规 |

> 注意：RWKV 的"状态"是每个会话独立的一份。多用户产品里，要么用"每会话一个状态"的方式（天然隔离），要么由应用层管理状态 ID 与用户映射——这是工程上需要设计好的点。
