# 第十一章 进阶：微调、State Tuning 与 RAG

想让 RWKV"更懂你的业务"，主要有三条路：**微调（Fine-tuning）**、**State Tuning（状态微调，RWKV 独有）** 和 **RAG（检索增强）**。这一章把三者讲清楚，并给出实践建议。

## 11.1 先搞清三种手段的区别

| 手段 | 改的是什么 | 成本 | 效果 |
| --- | --- | --- | --- |
| 提示工程（Prompt） | 不改模型，改输入 | 最低 | 一般，受上下文限制 |
| RAG（检索增强） | 不改模型，动态塞入资料 | 低 | 好，适合"查资料回答问题" |
| 微调（Fine-tuning） | 改模型权重 | 高（需 GPU） | 强，改变模型"能力/性格" |
| State Tuning | 只改隐藏状态 | 低（更快更省） | 强，像"调整心理状态"，个性化/对齐效果好 |

**一句话**：RAG 是"外挂知识"，微调是"改造大脑"，State Tuning 是"调整心情"。

## 11.2 微调流程总览

微调就是"拿你自己的数据，再训练一会儿模型"，让它学会你的领域/风格：

![微调流程](img/fig17_finetune_flow.png)

1. **准备数据集**：问答/对话/指令数据（如"用户问题 → 期望回答"）；
2. **格式化 + Tokenize**：把数据按模型的对话模板组织好；
3. **微调训练**：可选全参微调、LoRA（低秩适配，更省显存）、PEFT；
4. **导出权重**：.pth 或转 GGUF；
5. **部署 + 验证**：上线前用测试集评估。

## 11.3 数据格式：先准备"喂什么"

微调效果好不好，80% 取决于数据。RWKV 微调常用的数据格式（JSON Lines，每行一条）：

```json
{"text": "用户：我今天很沮丧。\n小暖：我能感觉到你今天很不好受，愿意和我聊聊发生了什么吗？"}
{"text": "用户：工作被领导批评了。\n小暖：被批评确实会让人难过。你先别急着自责，这次具体是因为什么呢？"}
```

要点：

- 数据要**多轮、真实、贴合你的业务**；
- 每条要**有明确期望的风格/回答**；
- 数量从几百条到几万条都可以，先从小数据集验证流程。

## 11.4 三种微调方式的取舍

| 方式 | 改的权重 | 显存需求 | 适合场景 |
| --- | --- | --- | --- |
| 全参微调（Full FT） | 所有参数 | 高 | 数据多、算力足、要彻底改造 |
| LoRA 微调 | 少量低秩矩阵 | 中 | 大多数场景，兼顾效果与成本 |
| State Tuning | 仅隐藏状态 | 低 | 个性化/对齐/角色扮演，又快又省 |

## 11.5 State Tuning：RWKV 的独家绝活

### 11.5.1 它是什么

**State Tuning（状态微调）** 是 RWKV 社区在 v6 迭代中发明的技术：**不修改模型权重，只微调"隐藏状态的初始值"**。

- 模型权重 = "大脑的神经连接"（决定基本能力）；
- 隐藏状态初始值 = "大脑此刻的心理状态 / 情绪 / 记忆基调"。

State Tuning 就是给模型"调整好心情再上场"：通过微调初始状态，让模型在特定任务/角色上表现更好。

### 11.5.2 为什么它很厉害

- **极其高效**：只调一个状态向量，参数极少，训练快、显存低；
- **效果相当**：被称为"最有效的 prompt tuning"，在**对齐（alignment）**任务上表现优秀；
- **迁移性好**：训练好的 State 可以迁移到别的同架构模型上复用；
- **Transformer 做不到**：Transformer 没有这种"可调且固定大小"的隐藏状态，这是 RNN 系架构独有的能力。

### 11.5.3 一句话理解

> 微调 = 给模型"换脑子"（改权重，重）；State Tuning = 给模型"调整心理状态"（改初始状态，轻），但都能让它在某类任务上表现更好。

### 11.5.4 使用方式（示意）

- 社区有 **RWKV-PEFT** 工具库提供 State Tuning 脚本；
- 训练得到的是一个 `.st` 格式的"状态文件"；
- 使用时在 RWKV-Runner / 推理代码里"挂载"这个 State（架构与参数规模必须与基底模型一致，如 x060 配 x060、7B 配 7B）。

| 检查项 | 基底模型 | State | 要求 |
| --- | --- | --- | --- |
| 架构 | RWKV-6（x060） | x060 | 必须一致 |
| 参数规模 | 7B | 7B | 必须一致 |
| 作用 | 提供完整模型权重 | 提供训练后的状态 | 两者配合使用 |

## 11.6 RAG：让模型"查资料"再回答

RAG（Retrieval-Augmented Generation，检索增强生成）解决的是"模型不知道你私有资料"的问题：**先从知识库里检索相关资料，再塞给模型生成回答**。

![RAG 应用架构](img/fig18_app_rag.png)

### 11.6.1 完整流程

1. **离线建库**：把企业文档/知识库切成小段 → 向量化（embedding）→ 存入向量数据库；
2. **在线问答**：用户提问 → 把问题向量化 → 在向量库检索最相关的片段；
3. **注入生成**：把检索到的片段拼进提示词 → 交给 RWKV 生成回答。

### 11.6.2 最小实现（用 Python）

```python
import chromadb
from sentence_transformers import SentenceTransformer

# 1. 准备向量库
client = chromadb.Client()
col = client.get_or_create_collection("kb")

# 2. 文档分块 + 入库（这里用简单的段落切分示意）
docs = ["RWKV 是一种无注意力 RNN 架构。", "RWKV-7 支持动态状态演化。", "..."]
chunks = [d.strip() for d in docs if d.strip()]
col.add(ids=[str(i) for i in range(len(chunks))], documents=chunks)

# 3. 检索 + 生成
def rag_answer(question):
    hits = col.query(query_texts=[question], n_results=3)
    context = "\n".join(hits["documents"][0])
    prompt = f"请根据以下资料回答问题：\n{context}\n\n问题：{question}\n回答："
    return chat(prompt)   # 复用第十章里的 chat 函数
```

### 11.6.3 为什么 RWKV 特别适合 RAG

- **长上下文便宜**：检索出的多段资料可以一起塞进去，RWKV 不心疼；
- **显存恒定**：即使知识片段很长，内存也不膨胀；
- **自带句嵌入**：RWKV 能输出高质量的句子向量，甚至可以直接当 embedding 模型用，省一套模型。

> 注意：RWKV-7 的 `/v1/embeddings` 返回的是随模型结构变化的多维状态数组，不能直接当作通用一维文本向量，需要按官方 API 说明处理。

## 11.7 三者的组合拳（推荐姿势）

在生产项目中，三者往往组合使用：

1. **基础能力**：用开源 RWKV-7 基底模型；
2. **领域知识**：用 RAG 接入私有知识库（成本低、更新快）；
3. **风格/角色**：用 State Tuning 或 LoRA 微调出想要的"性格"；
4. **即时控制**：用系统提示词做日常的"人设开关"。

这种"基底模型 + 检索 + 轻量微调"的架构，成本最低、效果最好、迭代最快，也是我们第十二章工程套用的主线。

## 11.8 微调避坑指南

| 坑 | 现象 | 解决办法 |
| --- | --- | --- |
| 数据太少 | 微调后变"复读机" | 数据量至少几百条；或改用 State Tuning |
| 格式不对 | 训练崩/回答乱 | 严格按对话模板格式化 |
| 过拟合 | 只会背训练集 | 加正则、降学习率、增数据多样性 |
| 显存不足 | OOM | 用 LoRA / QLoRA / State Tuning |
| 量化后变笨 | 回复质量下降 | 用 Q8_0 或更高精度微调/推理 |
