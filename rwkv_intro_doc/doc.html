第一章 一句话看懂 RWKV：写给完全零基础的你

如果你完全不懂神经网络、不懂 Transformer，也没关系。这一章用大白话，把 RWKV 到底是什么、为什么值得你花时间了解，讲得明明白白。

1.1 一段话讲清 RWKV

RWKV（读作 "R-W-K-V"，全称 Receptance Weighted Key Value，中文名"元始智能"）是一种大语言模型（LLM）的底层架构。所谓"架构"，你可以理解为模型的大脑结构——就像人脑和电脑主板都有不同的设计一样，现在市面上的 AI 模型（ChatGPT、文心、通义、Llama 等）大多采用一种叫 Transformer（Transformer） 的结构；而 RWKV 是另一种设计，它想用更省资源的方式，达到和 Transformer 差不多的聪明程度。

它的最大卖点可以浓缩成一句话：

**RWKV = 拥有 Transformer 级"聪明度"，但像老式 RNN 一样"又省内存、又省电、又能无限聊下去"的语言模型架构。**

换句话说，Transformer 是"性能天花板高但很费钱"的豪车；RWKV 是"性能接近、但油耗低、还能在乡间小路（普通电脑、手机）上跑"的混动车。

1.2 三个生活化的比喻

为了让你 30 秒内建立直觉，我们用三个比喻来理解 RWKV 的设计哲学：

比喻一：认真做笔记的学生 vs 每次重读整本书的学生。

  • Transformer 回答问题时，会把"从开头到现在的所有原文"重新读一遍（自注意力）。这样记得准，但书越长，它翻书越累（算力按平方增长）。
  • RWKV 像一位认真做笔记的学生，一边读一边把重点浓缩成一张"小抄"（隐藏状态），回答问题时只看小抄。小抄永远那么厚（内存恒定），但书再长它也不累。

比喻二：记性超好的账房先生。

Transformer 把每一笔交易（每个词）都留着，随时能精确翻出"三个月前某天上午的一笔账"（所以它细节回忆强，但账本越堆越大）。RWKV 只记一本"流水账摘要"，越早的信息记得越淡（指数衰减），但账本体积永远不变。

比喻三：混动车。

城市里走走停停（短文本）用电机（RNN 模式）省油；上高速（长文本、大吞吐）用发动机（Transformer 模式）有劲。RWKV 就装了两套"驱动"：训练时像 Transformer 一样能并行加速，推理时像 RNN 一样省内存。

1.3 为什么你需要关心它

现在大模型圈子里，几乎所有主流模型都是 Transformer。但 Transformer 有个"天生的痛"：

**序列越长，Transformer 越贵。** 计算量和内存随文本长度呈"平方级"增长。聊 100 句和聊 1000 句，成本差的不是 10 倍，而是 100 倍。

这个痛点带来了一系列现实问题：

  • 显存不够：想本地跑大模型，动辄要几十 GB 显存，普通电脑跑不动。
  • 长对话崩溃：多轮对话越聊越卡，甚至内存耗尽直接崩掉。
  • 长文档难处理：想让它"读完整本小说再总结"，成本高得离谱。
  • 部署成本高：云端推理的 GPU 费用按 token 算，长文本很烧钱。

RWKV 恰恰是为了解决这些问题而生的：内存固定、速度恒定、显存友好、CPU 都能跑、开源免费可商用。这也是为什么它在"边缘设备、长对话、低资源部署"这些场景里特别受关注。

第二章 基础铺垫：先认识 RNN 和 Transformer

要理解 RWKV 为什么特殊，得先知道它站在谁的肩膀上。这一章我们用最通俗的方式，把两个"前辈"——RNN 和 Transformer——讲清楚。它们正是 RWKV 想要"取其精华、去其糟粕"的对象。

2.1 什么是"序列"和"语言模型"

在进入架构之前，先明确两个概念：

序列（Sequence）：一串有先后顺序的数据。比如一句话"我喜欢吃苹果"，就是 5 个词组成的序列；一段心电图、一首歌的波形、一行股票价格，也都是序列。大语言模型要处理的，就是这种"有前后顺序"的文本。

语言模型（Language Model）：本质是一个"猜下一个词"的游戏。给它看"我喜欢吃____"，它预测下一个最可能是"苹果"还是"火锅"。GPT 能写文章、聊天，底层都是这一个动作：根据已看到的词，预测下一个词，然后不断重复。

所以任何语言模型都要解决一个核心问题：如何利用"前面看过的内容"来预测"下一个词"。RNN 和 Transformer 给出了两种完全不同的答案，RWKV 给出了第三种。

2.2 RNN：一边走一边记（循环神经网络）

RNN（Recurrent Neural Network，循环神经网络）是最早的答案之一，诞生于 1980-1990 年代，LSTM（长短期记忆网络）是它的著名改良版。

RNN 的思路非常朴素：我一边读文本，一边把"印象"记在一个小本子上（隐藏状态），读下一个词时，既看这个词，也翻一翻小本子。

但 RNN 有三个著名缺点：

  1. 健忘（梯度消失）：记性会随距离衰减，早期看的内容越传越淡，学不会"长距离依赖"。比如让它读一篇万字小说，它常常忘了开头。
  2. 不能并行（串行计算）：必须一个词一个词按顺序算，第 5 个词必须等第 4 个词算完。训练大模型时，GPU 无法同时发力，慢得离谱。
  3. 训练不稳：深层 RNN 容易出现梯度爆炸等问题。

所以 RNN 虽然"省"，但"笨且慢"，在大模型时代被 Transformer 取代了。

2.3 隐藏状态：理解 RWKV 的钥匙

"隐藏状态（hidden state / state）"这个词非常重要，因为 RWKV 的整套设计都是围绕它展开的。请务必理解：

隐藏状态 = 模型对"到目前为止看到的一切"的压缩摘要，相当于模型的"心理状态 / 记忆"。

想象你在追一部剧：你不需要记住每一帧画面，大脑里留下的是一份"剧情摘要"——主角是谁、发生了哪些关键事件、现在进展到哪。这份摘要会随着剧情不断更新。隐藏状态就是这个"剧情摘要"。

RNN 每读一个词，就更新一次隐藏状态；RWKV 也完全一样。理解"隐藏状态"就理解了 RWKV 的一半，因为 RWKV 的核心创新，就是设计了一套"特别会做摘要、摘要又能并行生成"的隐藏状态更新规则。

2.4 Transformer：注意力机制的颠覆者

2017 年，Google 发表《Attention Is All You Need》，提出 Transformer，彻底改变了 NLP 领域。它的核心是自注意力（Self-Attention）。

自注意力的直觉是：每个词在理解自己时，都要"看看"序列里所有其他词，并判断谁跟它关系大。 比如在"银行"这个词出现时，模型要判断上下文里的"存钱"还是"河岸"，来理解这里是"银行"还是"河岸"。

实现上，每个词会生成三个向量：

  • Query（查询）：我到底在找什么信息？
  • Key（键）：我是谁，我携带什么"检索标签"？
  • Value（值）：我携带的具体内容是什么？

然后每个 Query 会跟所有词的 Key 算相似度（打分），分数经过 softmax 变成"注意力权重"，再用这些权重去加权求和所有 Value。谁跟当前词关系大，谁的 Value 就贡献得多。

这样做的最大好处是：

  1. 记忆精确：每个词都能直接"翻旧账"，看任意远的词，没有"健忘"问题。
  2. 完全可并行：所有词之间的配对关系可以同时计算，GPU 全力开火，训练飞快。

正因如此，Transformer 成了 ChatGPT、Llama 等几乎所有现代大模型的基础，横扫 NLP。

2.5 Transformer 的痛：O(N²) 和 KV Cache

Transformer 再强，也有一个绕不开的代价——复杂度随序列长度 N 呈平方级增长（O(N²)）。

  • 计算上：N 个词两两配对，需要算 N×N 个分数。序列长度翻倍，计算量变 4 倍；翻 4 倍，计算量变 16 倍。
  • 内存上（KV Cache）：推理时，为了不再重复计算历史，模型会把每个历史词的 Key 和 Value 都缓存起来（叫 KV Cache），随对话/文本变长，缓存线性增长，最终吃掉所有显存。

这就是为什么"长文本"和"多轮长对话"对 Transformer 是噩梦：要么贵得离谱，要么内存爆掉。

2.6 两大架构优缺点一表流

特性 RNN（LSTM 等） Transformer
记忆机制 隐藏状态（固定大小） 自注意力 + KV Cache
训练并行 不能并行，串行慢 完全并行，训练快
推理内存 固定（O(1)） 随上下文增长（KV Cache）
长距离记忆 差（健忘/梯度消失） 强（任意距离直接关联）
计算复杂度 O(N) 线性 O(N²) 平方
记忆精确度 低（压缩摘要） 高（完整保留原文）

现在你应该看出来了：RNN 省但不强，Transformer 强但不省。 那能不能造一个"又强又省"的架构？这正是 RWKV 诞生的动机——它的所有设计，都是在回答这个问题。

**本页小结**：序列模型要解决"怎么记住前面看过的内容"。RNN 用"固定大小的隐藏状态"（省但记不牢）；Transformer 用"自注意力 + KV Cache"（记牢但费钱）。RWKV 想用 RNN 的"隐藏状态"思路，同时做到 Transformer 级别的效果和并行训练。

第三章 RWKV 到底是什么

有了 RNN 和 Transformer 的基础，现在我们可以正式认识 RWKV 了。这一章讲清楚它的名字、定义、出身和"家族归属"。

3.1 名字的含义：R-W-K-V

RWKV 这个名字不是随便取的，它来自架构中四个核心组件——而且这四个组件，恰好能帮你记住这个模型是怎么工作的：

字母 英文 中文 通俗理解 类比传统注意力
R Receptance 感受态 控制"过去的信息"要被接受多少，像一个开关/门控 类似 Q（查询）
W Weight 权重衰减 可训练的"遗忘系数"，决定记忆随时间衰减多快 相当于位置权重
K Key 键 代表"当前这个词是什么"，用于检索记忆 同注意力里的 K
V Value 值 代表"这个词携带什么信息内容" 同注意力里的 V

一句话记法：RWKV 用"K 和 V"把信息写进记忆，用"W"决定忘得多快，用"R"决定读出来多少——四个字母正好串起"写入→衰减→读出"的完整流程。

顺带一提：RWKV 项目的中文名叫"元始智能"。它也是中国第一个达到 GPT 级性能的开源语言模型。

3.2 一个准确的定义

用一句话定义它：

**RWKV 是一种"注意力免费（attention-free）"的循环神经网络（RNN）变体：它完全不含自注意力，用"可并行计算的线性注意力 + 固定大小的隐藏状态"来建模序列，从而同时获得 Transformer 的并行训练能力和 RNN 的恒定内存推理能力。**

拆开看三个关键词：

  1. 注意力免费（attention-free）：架构里 100% 没有传统自注意力，这是它和 Transformer 最根本的区别。
  2. 循环神经网络变体：它在推理时以"循环/递归"方式工作，每步只保留一份状态。
  3. 可并行训练：训练时又能把整个序列"摊开"并行计算，不牺牲训练速度。

  • 诞生：2021 年 8 月，RWKV 首个版本（v1）在 GitHub 的 RWKV-LM 仓库提交。
  • 里程碑：
  • 2022 年底：发布首个正式模型；
  • 2023 年：论文被 EMNLP 2023 收录；同年 9 月，RWKV 开源项目加入 Linux 基金会（AI & Data 基金会下的首个生成式 AI 托管项目）；

3.4 它属于哪一类架构（家族定位）

在大模型架构演化的版图上，RWKV 站在"高效序列模型"这一支里。理解这个定位，能帮你更好地看懂后面的对比：

  • Transformer 阵营（GPT、Llama、Qwen、DeepSeek 等）：用自注意力，性能天花板高，但 O(N²) 代价大。
  • RNN / 状态空间模型（SSM）阵营（LSTM、Mamba 等）：用状态代替注意力，线性/常数开销，但早期训练并行难。
  • RWKV 及同族（RWKV、Mamba、RetNet、Gated DeltaNet 等）：都试图"用状态记忆替代注意力"，在效率和性能之间找平衡。RWKV 的特点是把"训练并行"和"推理恒定开销"同时做到，并且是从 0.1B 到 7.2B 全系开源、能直接跑的模型之一。
**记住这句话**：RWKV 不是要"干掉" Transformer，而是提供另一种选择——在"长文本、低资源、边缘部署、超长对话"这些 Transformer 最吃力的地方，RWKV 的性价比优势会非常明显。

第四章 RWKV 的特殊之处：十大核心卖点

这一章我们把 RWKV"特殊在哪"讲透。这十条卖点，既是它吸引人的地方，也是和 Transformer 拉开差距的关键。建议逐条看，每条后面都配了"小白版解释"。

4.1 卖点一：100% 无自注意力

这是 RWKV 最根本、最反直觉的一条。Transformer 的灵魂是自注意力，而 RWKV 完全没有它，靠"时间混合（Time Mixing）+ 通道混合（Channel Mixing）"两个模块替代。

  • 小白版：别的模型靠"每个词和所有词互相打招呼"来理解；RWKV 不打招呼，靠一本不断更新的"笔记"。
  • 意义：正因为没有注意力，才没有"两两配对"的平方级计算，才引出了后面所有效率优势。

4.2 卖点二：线性复杂度 O(N)

RWKV 的时间复杂度随序列长度 线性增长（O(N)），而 Transformer 是平方级（O(N²)）。

  • 小白版：读 2 倍长的书，RWKV 花约 2 倍力气；Transformer 花约 4 倍力气。书越长差距越大。
  • 数据对比：4K 上下文时差距约 4 倍，32K 时差距可达 30 倍以上。

4.3 卖点三：恒定内存、没有 KV Cache

推理时 Transformer 要存"KV Cache"（历史每个词的键值），随对话增长线性膨胀；RWKV 只需一份固定大小的隐藏状态，无论上下文多长，内存占用不变。

  • 小白版：Transformer 是"越聊记事本越厚"，RWKV 是"永远同一本小抄"。
  • 实测：在 8GB 内存、无 GPU 的迷你主机上，RWKV-7 2.9B 连续 10 轮对话速度恒定，而同规模 Transformer 在第 6 轮就内存耗尽崩溃。

4.4 卖点四：恒定生成速度

因为没有 KV Cache，RWKV 每个 token 的生成时间与上下文长度无关——聊到第 100 轮和第 1 轮一样快。Transformer 越聊越慢（因为每生成一个新词，都要重新处理越来越长的缓存）。

  • 小白版：同样一句话，RWKV 第 1 句和第 1000 句回复速度一样；Transformer 越往后越卡。

4.5 卖点五：双模式（训练像 Transformer，推理像 RNN）

这是 RWKV 最巧妙的工程设计：同一套权重，有两种跑法。

  • 训练（GPT 模式 / 时间并行）：把整段文本一次性摊开，所有 token 并行计算 → 训练速度和 Transformer 相当。

  • 推理（RNN 模式 / 时间顺序）：一个词一个词地走，每步带上一步的状态 → 内存固定、延迟恒定。

  • 小白版：一辆车两种开法——高速用"并行巡航"，堵车用"单车道慢行"，都省油。

4.6 卖点六：长上下文 / "无限"上下文

理论上，因为内存固定、速度恒定，RWKV 可以处理非常长的上下文（社区常宣传"无限 ctxlen"），特别适合长文档和超长多轮对话。注意，这是"推理成本不随长度暴涨"，但模型对超长上下文的"实际记忆质量"仍有限制（这一点在第六章会详细讲）。

  • 小白版：它能"读完整本书再跟你聊"，而且读多长的书都不额外耗内存。

4.7 卖点七：State Tuning（状态微调）——独家绝活

RWKV 的隐藏状态可以直接被微调！这叫 State Tuning（状态微调）：不动模型权重，只微调"隐藏状态"，就能让模型在特定任务上表现更好。

  • 小白版：不用给模型"换脑子"，只给它"调整心情/记忆"，任务就变好了——又快又省。
  • 意义：这是 RNN 系架构独有的能力，Transformer 做不到（它没有这种可调的固定状态）。对个性化、角色扮演类应用特别有价值（第十一章会用到）。

4.8 卖点八：对硬件极友好

RWKV 推理时只做矩阵×向量运算，不需要 KV Cache，因此：

  • 支持 CPU 直接跑（无需 GPU）；
  • 量化友好，2.9B 的 Q8 量化模型约 3GB，Q4 更小；
  • 8GB 内存的旧电脑、树莓派都能跑起来；
  • 显存占用恒定，单卡可部署更大模型。

4.9 卖点九：开源、可商用

RWKV 模型、训练代码、推理内核均以 Apache 2.0 协议开源，属于 Linux 基金会项目。这意味着你可以自由使用、修改、商用，没有闭源模型的授权成本。对企业和个人项目都很友好。

4.10 卖点十：免费好用的句嵌入（Sentence Embedding）

RWKV 还能输出高质量的句子向量（句嵌入），可直接用于语义搜索、文本聚类、检索增强（RAG）等任务，相当于"语言模型 + 向量模型"二合一，省下一套嵌入模型的钱。

第五章 架构拆解：RWKV 内部长什么样

这一章我们钻进 RWKV 的内部，把它的"零件"一个个拆开看。别怕，我们会一直用"记忆"和"笔记"的比喻，公式只是顺便提一下。

5.1 整体结构：堆叠的残差块

RWKV 的整体骨架和 Transformer 很像：输入被切成 token → 向量化 → 经过 N 层相同的"块（block）"堆叠 → 输出预测。 每一层块都由两个子块组成：

  1. Time Mixing（时间混合）：负责"在时间轴上混合信息"，相当于注意力层的角色，是 RWKV 的记忆核心。
  2. Channel Mixing（通道混合）：负责"在每个位置上做特征加工"，相当于前馈网络（FFN）的角色。

从上图可以看到，两个子块之间都有残差连接（Residual）+ LayerNorm，和 Transformer 的"残差 + 归一化"套路一致。残差连接的意义：让信息能"抄近路"绕过复杂模块，既帮助训练稳定，也让深层网络可训练。

5.2 第一个零件：Token Shift（词元转移 / 短卷积）

这是 RWKV 的一个小但关键的技巧。在每个子块计算前，它会把"上一个时刻的输入"和"当前时刻的输入"按比例混合一下。

数学上就是线性插值：

Shift(x[t]) = μ · x[t] + (1 - μ) · x[t-1]

其中 μ 是混合系数（不同通道可以不同）。直观地说，它让每个位置"自带一点上一时刻的影子"，从而让模型在计算时能"摸到"邻近的历史信息。

  • 小白版：相当于每次动笔前，先瞥一眼自己刚写的上一句话，让上下文更连贯。
  • 为什么叫"短卷积"：它等价于一个核长度只有 2 的卷积，计算量几乎为零，却显著提升了性能。
  • 进阶版：在 RWKV-5/6 中，Token Shift 升级为"数据相关"的版本，让模型按内容决定混合比例。

5.3 第二个零件：Time Mixing / WKV 算子（记忆核心）

这是 RWKV 最重要的发明，用"WKV 算子"替代了注意力。它的流程可以拆成三步：

  1. 写入：当前词的 K（键）和 V（值）被写进"记忆状态 S"；
  2. 衰减：旧的记忆按"W（可学习的衰减系数）"指数级淡忘——越早的信息权重越低；
  3. 读出：用 R（感受态，类似查询）从记忆里加权读出信息，再经过门控得到输出。

用公式表达（RWKV-4 的经典形式）：

WKV 核心：output_t = R_t · ( Σ_{i<t}  exp(-w·(t-i)) · (K_i · V_i) + exp(u)·(K_t·V_t) ) / 分母
  • exp(-w·(t-i)) 就是按时间距离打折：离得越远，权重越小（但不会完全消失）。
  • 中间那个 u 是"当前时刻的额外权重"（因为当前信息通常最重要）。
  • R_t 决定"这条信息要不要影响我"。

为什么这样能代替注意力？ 注意力是"每个词和所有历史词两两打分"；而 WKV 把历史预先压缩进一个固定大小的状态 S，读的时候不再逐个比对，而是"一把抓出来再按新旧打折"。前者精确但贵，后者省但略微"糊"。

公式中的"分母"用于归一化，避免状态不断累加而爆炸。RWKV-4 用一个单独的状态保存归一化因子；RWKV-7 改进了归一化方式，这里不展开。

5.4 第三个零件：Channel Mixing（通道混合）

如果说 Time Mixing 管"时间"，那 Channel Mixing 就管"特征"。它在同一个时刻上，对词向量的各个维度（通道）做非线性加工，作用类似 Transformer 的前馈网络 FFN。

它同样用 R、K、V 结构，但"混合"发生在通道之间而非时间之间：

Channel Mixing：out = sigmoid(R) ⊙ ( W2 · gelu(W1 · K) ⊙ V )
  • 先用 gelu 做非线性变换；
  • 再用 R（感受态）做门控，决定"这些特征要不要被激活"；
  • 作用和 FFN 一样：提升模型的表达能力（把特征空间映射到更高维再压回来）。

5.5 它为什么"无注意力也能行"：三件套合力

把上面的零件拼起来，你就明白 RWKV 的记忆逻辑了：

机制 角色 负责的记忆类型
Token Shift 短程记忆 刚看到的邻近词
指数衰减状态（WKV） 长程记忆 整段历史的压缩摘要
R 感受态门控 选择性注意 决定"要不要理会某条信息"

三个机制合起来，用一份固定大小的状态装下整个上下文，需要哪段按权重调出来——这就是它没有注意力却"记得住"的原因。

5.6 与 Transformer 逐层"翻译"对照

为了方便学过 Transformer 的人理解，我们做一张"翻译表"：

Transformer RWKV 对应物 说明
自注意力（Self-Attention） Time Mixing（WKV） 都做"序列信息聚合"
Q/K/V R（感受态）+ K + V 角色类似，机制不同
位置编码（Positional） W 衰减 + Token Shift 用"时间衰减"隐含位置信息
前馈网络 FFN Channel Mixing 都做逐位置非线性变换
残差 + LayerNorm 残差 + LayerNorm 几乎一样
KV Cache（推理） 隐藏状态 S 一个是"完整历史"，一个是"压缩摘要"

核心差异浓缩成一句话：Transformer 靠"保存所有历史 + 两两比对"来记忆；RWKV 靠"压缩成一份状态 + 按新旧打折"来记忆。

5.7 双模式背后的数学视角

为什么"同一套权重"既能并行训练又能循环推理？关键在 WKV 的可分解性：

  • 推理（循环形式）：状态按步更新 S_t = f(S_{t-1}, x_t)，每步只依赖上一步 → 天然串行、固定内存。
  • 训练（并行形式）：因为衰减系数 w 与输入无关（RWKV-4 及以前），整条时间轴上的 WKV 可以写成"前缀和"（cumulative sum），一次性并行算出所有位置的输出 → GPU 全开。

RWKV-6/7 引入了"数据相关"的衰减和更复杂的更新，并行不再那么简单，官方用专门的 CUDA 内核（WKV kernel）来高效实现——这也是为什么用 RWKV 时通常建议开启官方内核加速（第九章会讲）。

**本页小结**：RWKV 块 = 输入 → Token Shift → Time Mixing（WKV 记忆）→ 残差+LN → Token Shift → Channel Mixing（特征加工）→ 残差+LN → 输出。记忆靠"写入(K,V)→衰减(W)→读出(R)"三步完成，固定大小、可并行训练、可循环推理。

第六章 和 Transformer 到底差在哪：全面对比

这一章我们做一次"体检式"对比，把 RWKV 和 Transformer 从机制、复杂度、显存、训练、推理、效果、生态等各个维度掰开揉碎比较一遍。读完这一章，你对"什么时候选 RWKV、什么时候选 Transformer"会有一个清晰的判断。

6.1 一句话总结差异

先给你一个"总纲"，后面的所有细节都是它的展开：

Transformer：记忆靠"保存全部历史 + 两两比对"，精确但昂贵（O(N²)）。 RWKV：记忆靠"压缩成一份固定状态 + 按新旧打折"，便宜（O(N)）但略"糊"。

  • Transformer 像"图书馆"，每一本书（每个 token 的 K/V）都原样保留，查资料时逐本翻阅，越大的图书馆越贵。
  • RWKV 像"读书笔记"，把读过的内容浓缩成固定厚度的笔记本，随时翻、越翻越薄的成本，但记的是"摘要"而不是"原文"。

6.2 机制层面的对比：注意力 vs 状态

6.2.1 信息聚合方式

Transformer（自注意力）：

  1. 每个词生成 Q（查询）、K（键）、V（值）三个向量；
  2. 每个词用 Q 与"序列里所有词的 K"逐一打分（点积），得到 N 个注意力分数；
  3. softmax 归一化成权重；
  4. 用权重对 N 个 V 做加权求和，得到该词的输出。

这个过程对"序列内任意两个词"都做了一遍配对，所以叫"全对全（all-to-all）"。它的好处是任意距离都能直接关联（远亲也能翻到），坏处是计算量和内存随 N 平方增长。

RWKV（WKV 线性注意力）：

  1. 每个词用 K、V 把信息"写进"一个固定大小的记忆状态 S；
  2. 旧记忆按可学习的衰减系数 W 指数级淡忘；
  3. 每个词用 R（感受态，类似 Q）从状态 S 中"读出"信息，再经门控输出。

它不需要两两配对，只维护一份状态，所以计算量是 O(N)、内存是 O(1)。

6.2.2 记忆的"精确度"差异

这是两者最本质的取舍：

维度 Transformer RWKV
记忆载体 全部历史 token 的 K/V（KV Cache） 固定大小的隐藏状态 S
能否精确"翻旧账" 能，任意位置的原文都能精确加权 不能，只保存压缩后的摘要
长文本信息密度 越高（原文都在） 受状态容量限制
检索方式 逐个 token 两两打分 从状态中一次读出 + 衰减加权
类比 完整录音 / 完整账本 会议纪要 / 流水摘要

一个重要的事实：Transformer 的"精确回忆"在长上下文里是优势，但代价是"贵"。RWKV 用"摘要"换来了"便宜"，在大多数实际任务里，摘要已经够用；只有少数需要"逐字精确引用原文"的任务（比如某些法律文书检索），Transformer 仍占优。

6.3 复杂度对比：O(N²) vs O(N)

6.3.1 为什么 Transformer 是 O(N²)

自注意力要算一个 N×N 的注意力矩阵：N 个词，每个词要和 N 个词打分。所以：

  • 序列长度 N=1K → 需要约 100 万次配对；
  • N=4K → 约 1600 万次；
  • N=32K → 约 10 亿次。

长度翻倍，计算量变 4 倍（平方）；长度翻 4 倍，计算量变 16 倍。

6.3.2 为什么 RWKV 是 O(N)

RWKV 的 WKV 算子每来一个 token，只做一次"固定大小的状态更新 + 一次读出"，和"之前有多少词"无关。所以：

  • N=1K → 约 1K 次操作；
  • N=32K → 约 32K 次操作。

长度翻倍，计算量约翻倍（线性），这才是"长上下文不心疼"的根本原因。

6.3.3 数字对照表（示意）

上下文长度 Transformer 相对成本 RWKV 相对成本 差距
1K 1 1 持平
4K 16 4 约 4 倍
16K 256 16 约 16 倍
64K 4096 64 约 64 倍
256K 65536 256 约 256 倍

注意：这是"注意力部分"的理论复杂度对比，实际推理中 Transformer 有 FlashAttention 等优化、RWKV 有专用 CUDA 内核，比例会有所变化，但"随长度增长的趋势"不变——长度越长，RWKV 的性价比优势越大。

6.4 推理资源对比：KV Cache vs 隐藏状态

6.4.1 KV Cache 是什么

Transformer 推理时，为避免重复计算历史，会把每个已处理 token 的 K、V 向量缓存下来，这就是 KV Cache。它的大小随序列长度线性增长：上下文 4K 的 7B 模型，KV Cache 可能占数 GB 显存；64K 时就非常可观。

6.4.2 RWKV 为什么没有 KV Cache

RWKV 推理时只保留一份固定大小的隐藏状态 S（比如 7B 模型约 1-2GB，且与上下文长度无关）。无论你聊 100 句还是 10000 句，内存占用不变。

项目 Transformer RWKV
每轮新增内存 新增每个 token 的 K/V 无（状态原地更新）
长对话表现 越聊越慢，可能内存耗尽 速度、内存恒定
单次生成延迟 随上下文增长 恒定
极端长上下文 容易 OOM 崩溃 稳定可续

6.4.3 实战含义

对"多轮长对话"这类场景，差别是能不能用的区别：RWKV 聊到第 100 轮和第 1 轮一样快；Transformer 则在某轮开始后逐轮变慢，最终显存耗尽报错。这也是我们后续要把它套用到"AI 陪伴 / 情感智能体"上的核心原因之一。

6.5 训练方式对比：都支持并行，但代价不同

6.5.1 Transformer：天然并行

自注意力对序列内所有 token 同时计算，训练时 GPU 可以"全开"，所以训练效率极高。这是它统治大模型时代的核心竞争力。

6.5.2 RWKV：双模式并行

RWKV 的巧妙之处在于"同一套权重，两种跑法"：

  • 训练（GPT 模式）：把整段序列"摊开"，利用 WKV 的可分解性（前缀和），一次性并行算出所有位置的输出 → 训练速度和 Transformer 相当；
  • 推理（RNN 模式）：一个词一个词走，每步更新状态 → 内存固定、延迟恒定。

6.5.3 训练显存对比

因为 RWKV 不需要保存"每个 token 的 K/V 用于反向传播"（Transformer 训练时要保存大量中间激活），RWKV 的训练显存通常明显低于同规模 Transformer，这让单卡微调变得可行。

训练维度 Transformer RWKV
序列并行 支持 支持（GPT 模式）
反向传播中间量 大（每层每 token） 相对小（状态式）
单卡微调友好度 一般（常用 LoRA） 好（显存更低）
长序列训练 昂贵 更省

6.6 效果对比：谁更强？

"谁更强"不能脱离场景和规模。客观地看：

6.6.1 RWKV 的强项

  • 多语言：RWKV-7 在 3B 规模的多语言 benchmark 上刷新 SOTA，非英语语言尤其突出；
  • 状态追踪类推理：RWKV-7 论文证明它能完成"状态追踪"、识别所有正则语言，理论上能表达超出 Transformer 受限复杂度类（TC0）的一些任务；
  • 少样本学习（in-context learning）：RWKV-7 是一个"元上下文学习器"，在每个 token 上对状态做"上下文梯度下降"式的自我调整；
  • 稳定长程依赖：因指数衰减+Token Shift，长文本的连贯性表现稳定。

6.6.2 Transformer 的强项

  • 极致长上下文的精确回忆：能精确引用任意位置的原文；
  • 复杂推理 benchmark（如某些数学、代码题）：在超大模型规模下，Transformer 生态更成熟、效果天花板更高；
  • 生态成熟度：训练框架、算子、工具链、文档、第三方支持都远超 RWKV。

第七章 版本进化史与"为什么它真的能行"

这一章回答两个问题：RWKV 是怎么一步步进化到今天这个样子的？ 以及为什么一套"没有注意力"的循环网络，能取得接近 Transformer 的效果？ 理解这两点，你就真正"懂"了 RWKV。

7.1 进化时间线总览

RWKV 从 2021 年到现在经历了 8 个主要版本，每个版本都在解决上一代的核心瓶颈：

版本 代号/年份 核心突破 一句话说明
v1 2021 长卷积替代注意力 首次提出 Time-mix + Channel-mix 结构，验证方向
v2/v3 2022 实现 RNN 推理模式 让模型真正以"循环"方式工作，发布首个可用模型
v4 2023 首个 GPT 级大模型 性能达到 GPT 同级别，论文被 EMNLP 2023 收录
v5 Eagle，2024 多粒度注意力、矩阵状态 把状态从"向量"升级为"矩阵"，表达能力更强
v6 Finch，2024 数据相关衰减、World 14B 引入动态衰减与更多语言覆盖，开源 14B 多语言模型
v7 Goose，2025 动态状态演化（DSE） 突破线性注意力表达力上限，3B 多语 SOTA
v8 实验阶段，2025~ DeepEmbed / ROSA 等 探索稀疏化、混合架构（RWKV-7s）、在线后缀自动机

7.2 v1–v3：概念验证期

  • v1（2021）：彭博在研究中发现"显式衰减"和"Token Shift（短卷积）"能显著提升 Transformer，之后又借鉴了 Apple 的 AFT（Attention Free Transformer）论文思路，把两者结合，提出了 RWKV 的第一个版本。此时它更接近"线性 Transformer"，每个时间步仍依赖全部历史。
  • v2/v3（2022）：关键转变——把模型改成真正的 RNN 推理模式：只保留一份隐藏状态，一个词一个词往下走。这让内存从"随历史增长"变成了"恒定"，为后续所有效率优势打下基础。

这一时期的意义：证明了"去掉注意力 + 用状态记忆"这条路能走通，且参数量可以很小（如 27M）也能有不错的效果。

7.3 v4：里程碑——首个 GPT 级 RNN

RWKV-4 是整个项目最重要的里程碑：

  • 把 Time-mix 的公式固定为经典的"指数衰减 + 当前项额外权重"形式；
  • 首次做到与 GPT 同级别的效果（在部分 benchmark 上）；
  • 发布 1.5B、3B、7B 等规模的开源模型；
  • 2023 年论文被 EMNLP 2023 收录，同年 9 月项目加入 Linux 基金会。

它的意义：证明了"无注意力架构"不只是玩具，而是能真正达到大模型水平的产品级方案。

7.4 v5 Eagle：从"向量状态"到"矩阵状态"

RWKV-5 引入多粒度注意力，把状态从"向量"升级为"矩阵"：

  • 更多通道独立管理自己的记忆，类似"分了很多本笔记，每本记录不同方面的信息"；
  • 表达能力提升，但也带来更大的状态和更复杂的实现；
  • 是迈向"动态状态"的重要中间步骤。

7.5 v6 Finch：数据相关的衰减 + World 模型

RWKV-6 的关键词是"动态"：

  • 衰减系数不再是一成不变的固定值，而是根据输入内容动态决定（数据相关衰减）——模型可以自己决定"这条信息该记多久"；
  • 发布 RWKV-6 World 14B 多语言模型，覆盖中英日德法等大量语言；
  • 社区在此期间发展了 State Tuning（状态微调） 技术（见第十一章）。

它的意义：RWKV 从"通用高效架构"走向"多语言、多任务的世界模型"，应用面大幅扩展。

7.6 v7 Goose：动态状态演化（Dynamic State Evolution）

RWKV-7 是目前社区公认的基准，论文于 2025 年 3 月公开，官方称其为 RWKV-7 "Goose"。它解决了线性注意力长期以来的"表达力天花板"问题。

7.6.1 旧线性注意力的局限

在 v4–v6 里，状态更新是"写进去就固定"：

S[t] = 衰减 · S[t-1] + K · V

问题在于：记忆只能"写进去"，不能"改错"。如果模型一开始记错了某条信息，后面无法修正，这会限制它在某些推理任务上的表现。

7.6.2 动态状态演化（DSE）

RWKV-7 的核心创新是 Dynamic State Evolution（动态状态演化），本质是广义 Delta 规则（generalized delta rule）：

S[t] = S[t-1] · D[t] + 基于“误差”的更新

直觉是：模型每一步会先从状态里"读出"一个预测，然后拿真实输入和预测对比，算出误差，再用误差修正记忆——就像学生做完题对答案，发现错了就"改作业"。这样一来：

  • 记忆可以自我修正，而不是只进不出；
  • 模型变成"元上下文学习器"：在每个 token 上对状态做类似"上下文梯度下降"的调整；
  • 论文证明它能完成"状态追踪"，可识别所有正则语言 → 表达力超过注意力受限的 TC0 复杂度类。

7.6.3 v7 的效果

  • 在 3B 规模的多语言任务上刷新 SOTA；
  • 在"状态追踪"类推理任务上表现突出；
  • 同时保持了训练可并行、推理常数开销的优势；
  • 官方称它适合 LLM 与多模态应用。

7.7 v8 与未来：实验与混合

截至 2026 年，RWKV-8 仍处于实验阶段，公开的方向包括：

  • DeepEmbed：面向边缘设备的稀疏设计，解决 MoE（专家混合）显存占用问题；
  • DeepEmbedAttention：精简 KV Cache，特别适合混合架构（RWKV-7s）；
  • ROSA（RWKV Online Suffix Automaton）机制：为更强大的记忆与检索铺路；
  • 同时社区出现 RWKV-X 等混合架构（RWKV + 稀疏注意力），用于补强"极端细节的精确回忆"。

趋势判断：RWKV 正在走"纯 RNN → 动态状态 → 混合/稀疏化"的路线，未来大概率会是"状态记忆为主 + 必要处稀疏注意力"的混合形态。

7.8 为什么"没有注意力"也能行：理论直觉

很多人的第一反应是：没有注意力，怎么捕捉词与词的关系？答案藏在三件事的合力里。

7.8.1 三个机制各司其职

机制 负责的记忆类型 通俗类比
Token Shift 短程记忆（邻近词） 动笔前瞥一眼上一句
指数衰减状态（WKV） 长程记忆（整段历史） 一直更新的读书笔记
R 感受态门控 选择性注意 决定"这条要不要影响我"

7.8.2 为什么 RNN 会"健忘"，而 RWKV 不会

传统 RNN（如 LSTM）的"健忘"源于梯度在时间轴上连乘导致梯度消失。RWKV 用"指数衰减 + 显式可学习的 W"直接控制了信息在时间上的保留程度，而不是靠训练中去隐式学习——这让长程信息有保障地被保留，且 Token Shift 保证邻近信息不丢。

7.8.3 表达力：从"写死"到"可修正"

  • v4–v6 的状态更新是"只写不改"，表达力有上限；
  • v7 的 DSE 让状态可修正、可演化，表达力大幅提升；
  • 论文证明其能表达超出 TC0 的任务，这是线性注意力家族首次被证明可以做到。

7.8.4 训练为什么能并行（可分解性）

关键在于衰减结构可以写成"前缀和"：

  • 当衰减系数与输入无关时（v4 及以前），整条时间轴的 WKV 可以一次性并行算出来；
  • v6/v7 引入数据相关衰减后，并行不再平凡，官方用专门的 CUDA 内核（WKV kernel）高效实现；
  • 所以"用 RWKV 时通常建议开启官方内核加速"（详见第九章）。

7.9 为什么社区会关注它：一句话总结

RWKV 的价值不在于"替代所有模型"，而在于它证明了：

"聪明 + 便宜 + 省内存"可以同时存在。 它把 RNN 的省、Transformer 的强，用一套优雅的"状态记忆"设计统一了起来，并持续在表达力上逼近甚至超越注意力受限的模型。

**本章小结**：RWKV 从 2021 年的概念验证，到 v4 达到 GPT 级，再到 v7 "Goose" 的动态状态演化与超 TC0 表达力，一步步解决了"线性注意力的表达力天花板"。它之所以"没有注意力也能行"，靠的是 Token Shift（短程）+ 指数衰减状态（长程）+ R 门控（选择）+ v7 的可修正状态四者合力。

8.3 方式一：Ollama（最推荐给新手）

8.3.1 安装 Ollama

  • Windows / macOS：去 ollama.com 下载安装包，双击安装即可；
  • Linux：
curl -fsSL https://ollama.com/install.sh | sh

安装完成后，在终端输入 ollama --version 能输出版本号即成功。

8.3.2 拉取并运行 RWKV 模型

RWKV 社区成员 @MollySophia 维护了官方的 RWKV-7 模型库。直接运行：

# 运行 RWKV-7 G1 2.9B（推荐，默认带思考模式）
ollama run mollysama/rwkv-7-g1:2.9b

Ollama 会自动下载模型并进入对话界面，像和 ChatGPT 聊天一样直接打字。常见参数：

模型 tag 说明
mollysama/rwkv-7-g1:2.9b 2.9B，Q8_0 量化，默认带思考模式
mollysama/rwkv-7-g1:1.5b 1.5B，更轻量
mollysama/rwkv-7-g1:2.9b-thinkdisabled 关闭思考模式（更快）
mollysama/rwkv-7-world:2.9b 老版 World 模型（不推荐，G1 更全面）

提示：默认思考模式下，可以用 /set nothink 和 /set think 在终端里随时切换思考模式开关。

Ollama 默认在 http://localhost:11434 提供 API，几乎和 OpenAI 接口一致，方便程序调用：

curl http://localhost:11434/api/chat -d '{

  "messages": [{"role": "user", "content": "用一句话介绍 RWKV"}],
  "stream": false

8.4 方式二：RWKV-Runner（图形界面）

如果你更习惯"点鼠标"，用 RWKV-Runner（rwkv.cn 提供）体验最好：

  1. 去 rwkv.cn 下载 RWKV-Runner 安装包（支持 Win/macOS/Linux）；
  2. 打开软件，选择模型文件（.pth 或 .gguf 都支持）；
  3. 选择"后端/Strategy"： - 默认用 RWKV Pip（cuda fp16 或 cpu fp32）； - NVIDIA 显卡 + RWKV-7 可切换 Albatross（albatross workers=1 batch=32）做性能对比； - GGUF 量化模型用 llama.cpp 后端； - 苹果/AMD 等 WebGPU 设备用 WebGPU 后端；
  4. 点击启动，即可在自带聊天界面使用，还能挂载 State、调整 Temperature 等参数。

后端小知识：后端（Backend）决定"哪套程序加载并运行模型"；Strategy 是"加载配置"（设备、精度、上下文长度）；量化是"权重的保存精度"。三者不要混淆。

8.5 方式三：llama.cpp + GGUF（低配设备最爱）

llama.cpp 是 CPU 也能高效跑模型的老牌工具，RWKV 的 GGUF 量化模型对它支持良好。

8.5.1 获取 GGUF 模型

RWKV 的 GGUF 模型可以从 Hugging Face 集合（如 zhiyuan8/models）下载，推荐用 FP16 或 Q8_0 量化档（更低的 Q5/Q4 会明显降低回复质量）。

8.5.2 命令行运行

# llama-cli 交互式对话

第九章 推理实战：命令行、API 与采样参数

9.1 一次推理的内部流程

无论是命令行还是 API，一次推理都要走下面这条流水线：

  1. Tokenize（分词）：把文本切成 token（词元/子词），比如"我喜欢吃苹果"切成若干 token；
  2. 前向计算（forward）：把 token 序列喂给 RWKV，逐层更新状态，输出下一个 token 的概率分布；
  3. 采样（sample）：按概率（结合温度、Top_P 等参数）选出一个 token；
  4. Decode（解码）：把选出的 token 拼回文本，输出；
  5. 重复 2–4，直到生成结束标记（EOS）或达到最大长度。

RWKV 的关键细节：多轮对话时，"状态 S"会一直往下传——所以它不需要每次都重新处理整段历史，这也是它"聊得再久也不慢"的秘密。

9.4 采样参数详解：怎么让 AI"听话"

这些参数决定生成的"随机性 vs 稳定"，非常重要：

参数 作用 建议
temperature 温度：越高越随机、越有创意；越低越确定 0.6–0.9 创作；0.1–0.3 事实/代码
top_p 核采样：只从累计概率前 P 的 token 里选 0.8–0.95 常用
top_k 只从概率最高的 K 个 token 里选 40–80 常用
repeat_penalty 重复惩罚：抑制说车轱辘话 1.0–1.3
max_tokens 单次最多生成多少个 token 按需求设置
num_ctx 上下文窗口长度 RWKV 可放心开大

调参口诀：

  • 想要稳定、专业的回答（客服、代码、事实问答）→ temperature 调低（0.2–0.4）；
  • 想要有创意、会聊天（写故事、闲聊、情感陪伴）→ temperature 调高（0.7–1.0）；
  • 发现重复啰嗦 → 调大 repeat_penalty 或适当降 temperature。

10.2 最小可用：加载模型并生成一句话

from rwkv.model import RWKV
from rwkv.utils import PIPELINE, PIPELINE_ARGS
import torch

# 1. 指定模型文件（.pth）与策略
model_path = "models/rwkv7-g1-2.9b-20250519-ctx4096.pth"

# strategy = "cpu fp32"         # 纯 CPU 用这个

    temperature=0.8,

    top_k=80,
    repetition_penalty=1.1,

10.3 多轮对话：用"状态 S"实现真正的连续记忆

RWKV 最大的魅力在于：状态 S 可以在多轮之间传递。这样模型不是靠"把所有历史再喂一遍"，而是带着压缩后的记忆继续聊。

from rwkv.model import RWKV
from rwkv.utils import PIPELINE, PIPELINE_ARGS

model = RWKV(model="models/rwkv7-g1-2.9b.pth", strategy="cuda fp16")
pipeline = PIPELINE(model, "rwkv_vocab_v304")

state = None  # 状态从空开始

def chat(user_msg, state):
    # 组装提示：system + 当前用户消息
    prompt = f"你是一个温柔的心理陪伴助手。\n\n用户：{user_msg}\n助手："
    args = PIPELINE_ARGS(temperature=0.85, top_p=0.95, max_gen=150,
                         repetition_penalty=1.1)
    # generate 会返回 (文本, 更新后的 state)
    text, state = pipeline.generate(prompt, token_count=150, args=args,
                                    state=state)
    return text.strip(), state

# 第一轮
reply1, state = chat("我今天加班到很晚，好累……", state)
print("助手：", reply1)

# 第二轮：模型还记得上一轮的情绪
reply2, state = chat("能不能给我讲个放松的小故事？", state)
print("助手：", reply2)

为什么这是"记忆"而不是"复读"？ 因为 state 是压缩后的摘要，不是把原文再抄一遍。这既省内存，又让"越聊越懂你"成为可能。

10.4 状态保存与恢复：跨会话续聊（杀手锏）

RWKV 的状态可以序列化保存到硬盘，下次启动时直接恢复——相当于"模型记得你是谁、你们聊过什么"。

import pickle

def save_state(state, path="my_chat_state.pkl"):
    # state 通常是 list/tuple 结构，pickle 即可
    with open(path, "wb") as f:
        pickle.dump(state, f)
    print(f"状态已保存到 {path}")

def load_state(path="my_chat_state.pkl"):
    with open(path, "rb") as f:
        return pickle.load(f)

完整的多会话流程：

# 场景：AI 陪伴机器人，每个用户有专属记忆
def get_state_for(user_id):
    try:
        return load_state(f"state_{user_id}.pkl")
    except FileNotFoundError:
        return None  # 新用户，从空白记忆开始

def on_user_message(user_id, msg):
    state = get_state_for(user_id)          # 取出该用户的记忆
    reply, new_state = chat(msg, state)     # 带着记忆对话
    save_state(new_state, f"state_{user_id}.pkl")  # 存回记忆
    return reply

这一步就是"角色记忆可持续"的工程实现——Transformer 要实现类似效果，要么把历史全喂进去（越来越贵），要么自己做一套记忆系统；RWKV 直接给你原生状态，天然适合"陪伴/长期关系"类产品。

10.5 流式输出：打字机效果

def chat_stream(user_msg, state):
    prompt = f"用户：{user_msg}\n助手："
    args = PIPELINE_ARGS(temperature=0.85, top_p=0.95,
                         max_gen=150, repetition_penalty=1.1)

    out = ""
    for chunk in pipeline.generate(prompt, token_count=150, args=args,
                                   state=state, stream=True):
        # 每次只返回新增的几个 token
        print(chunk, end="", flush=True)
        out += chunk
    print()
    return out

流式输出的价值：长回答时用户不需要干等，体验和 ChatGPT 一样"一个字一个字蹦出来"。

10.6 完整版：一个可用的"陪伴聊天机器人"

把上面的拼起来，写一个最小可用的完整脚本：

"""rwkv_chatbot.py —— 一个带长期记忆的最小陪伴机器人"""
import pickle
from rwkv.model import RWKV
from rwkv.utils import PIPELINE, PIPELINE_ARGS

MODEL_PATH = "models/rwkv7-g1-2.9b-20250519-ctx4096.pth"
STRATEGY = "cuda fp16"

model = RWKV(model=MODEL_PATH, strategy=STRATEGY)
pipeline = PIPELINE(model, "rwkv_vocab_v304")
SYSTEM = "你是小暖，一个温柔耐心、善于倾听的心理陪伴助手。"


def make_state(user_id):
    try:
        with open(f"state_{user_id}.pkl", "rb") as f:
            return pickle.load(f)
    except FileNotFoundError:
        return None


def keep_state(user_id, state):
    with open(f"state_{user_id}.pkl", "wb") as f:
        pickle.dump(state, f)


def respond(user_id, user_msg):
    state = make_state(user_id)
    prompt = f"{SYSTEM}\n\n用户：{user_msg}\n小暖："
    args = PIPELINE_ARGS(temperature=0.85, top_p=0.95,
                         max_gen=200, repetition_penalty=1.1)
    reply, state = pipeline.generate(prompt, token_count=200,
                                     args=args, state=state)
    keep_state(user_id, state)
    return reply.strip()


if __name__ == "__main__":
    uid = "alice"
    while True:
        msg = input("你：")
        if msg in ("exit", "quit"):
            break
        print("小暖：", respond(uid, msg))

这个 40 行的脚本，已经实现了：

  • 多轮对话的连续记忆（状态传递）；
  • 跨会话的长期记忆（状态持久化到磁盘）；
  • 角色人设（system prompt）；
  • 可扩展：加 TTS 语音、情感检测、情绪追踪，就是一个完整的 AI 陪伴产品原型（第十二章展开）。

第十一章 进阶：微调、State Tuning 与 RAG

想让 RWKV"更懂你的业务"，主要有三条路：微调（Fine-tuning）、State Tuning（状态微调，RWKV 独有） 和 RAG（检索增强）。这一章把三者讲清楚，并给出实践建议。

11.1 先搞清三种手段的区别

手段 改的是什么 成本 效果
提示工程（Prompt） 不改模型，改输入 最低 一般，受上下文限制
RAG（检索增强） 不改模型，动态塞入资料 低 好，适合"查资料回答问题"
微调（Fine-tuning） 改模型权重 高（需 GPU） 强，改变模型"能力/性格"
State Tuning 只改隐藏状态 低（更快更省） 强，像"调整心理状态"，个性化/对齐效果好

一句话：RAG 是"外挂知识"，微调是"改造大脑"，State Tuning 是"调整心情"。

11.2 微调流程总览

微调就是"拿你自己的数据，再训练一会儿模型"，让它学会你的领域/风格：

  1. 准备数据集：问答/对话/指令数据（如"用户问题 → 期望回答"）；
  2. 格式化 + Tokenize：把数据按模型的对话模板组织好；
  3. 微调训练：可选全参微调、LoRA（低秩适配，更省显存）、PEFT；
  4. 导出权重：.pth 或转 GGUF；
  5. 部署 + 验证：上线前用测试集评估。

11.3 数据格式：先准备"喂什么"

微调效果好不好，80% 取决于数据。RWKV 微调常用的数据格式（JSON Lines，每行一条）：

{"text": "用户：我今天很沮丧。\n小暖：我能感觉到你今天很不好受，愿意和我聊聊发生了什么吗？"}
{"text": "用户：工作被领导批评了。\n小暖：被批评确实会让人难过。你先别急着自责，这次具体是因为什么呢？"}

要点：

  • 数据要多轮、真实、贴合你的业务；
  • 每条要有明确期望的风格/回答；
  • 数量从几百条到几万条都可以，先从小数据集验证流程。

全参微调（Full FT） 所有参数 高 数据多、算力足、要彻底改造

11.5 State Tuning：RWKV 的独家绝活

11.5.1 它是什么

State Tuning（状态微调） 是 RWKV 社区在 v6 迭代中发明的技术：不修改模型权重，只微调"隐藏状态的初始值"。

  • 模型权重 = "大脑的神经连接"（决定基本能力）；
  • 隐藏状态初始值 = "大脑此刻的心理状态 / 情绪 / 记忆基调"。

State Tuning 就是给模型"调整好心情再上场"：通过微调初始状态，让模型在特定任务/角色上表现更好。

11.5.2 为什么它很厉害

  • 极其高效：只调一个状态向量，参数极少，训练快、显存低；
  • 效果相当：被称为"最有效的 prompt tuning"，在对齐（alignment）任务上表现优秀；
  • 迁移性好：训练好的 State 可以迁移到别的同架构模型上复用；
  • Transformer 做不到：Transformer 没有这种"可调且固定大小"的隐藏状态，这是 RNN 系架构独有的能力。

11.5.3 一句话理解

微调 = 给模型"换脑子"（改权重，重）；State Tuning = 给模型"调整心理状态"（改初始状态，轻），但都能让它在某类任务上表现更好。

11.5.4 使用方式（示意）

  • 社区有 RWKV-PEFT 工具库提供 State Tuning 脚本；
  • 训练得到的是一个 .st 格式的"状态文件"；
  • 使用时在 RWKV-Runner / 推理代码里"挂载"这个 State（架构与参数规模必须与基底模型一致，如 x060 配 x060、7B 配 7B）。
检查项 基底模型 State 要求
架构 RWKV-6（x060） x060 必须一致
参数规模 7B 7B 必须一致
作用 提供完整模型权重 提供训练后的状态 两者配合使用

11.6 RAG：让模型"查资料"再回答

RAG（Retrieval-Augmented Generation，检索增强生成）解决的是"模型不知道你私有资料"的问题：先从知识库里检索相关资料，再塞给模型生成回答。

11.6.1 完整流程

  1. 离线建库：把企业文档/知识库切成小段 → 向量化（embedding）→ 存入向量数据库；
  2. 在线问答：用户提问 → 把问题向量化 → 在向量库检索最相关的片段；
  3. 注入生成：把检索到的片段拼进提示词 → 交给 RWKV 生成回答。

11.6.2 最小实现（用 Python）

import chromadb
from sentence_transformers import SentenceTransformer

# 1. 准备向量库
client = chromadb.Client()
col = client.get_or_create_collection("kb")

# 2. 文档分块 + 入库（这里用简单的段落切分示意）
docs = ["RWKV 是一种无注意力 RNN 架构。", "RWKV-7 支持动态状态演化。", "..."]
chunks = [d.strip() for d in docs if d.strip()]
col.add(ids=[str(i) for i in range(len(chunks))], documents=chunks)

# 3. 检索 + 生成
def rag_answer(question):
    hits = col.query(query_texts=[question], n_results=3)
    context = "\n".join(hits["documents"][0])
    prompt = f"请根据以下资料回答问题：\n{context}\n\n问题：{question}\n回答："
    return chat(prompt)   # 复用第十章里的 chat 函数

11.6.3 为什么 RWKV 特别适合 RAG

  • 长上下文便宜：检索出的多段资料可以一起塞进去，RWKV 不心疼；
  • 显存恒定：即使知识片段很长，内存也不膨胀；
  • 自带句嵌入：RWKV 能输出高质量的句子向量，甚至可以直接当 embedding 模型用，省一套模型。

注意：RWKV-7 的 /v1/embeddings 返回的是随模型结构变化的多维状态数组，不能直接当作通用一维文本向量，需要按官方 API 说明处理。

11.7 三者的组合拳（推荐姿势）

在生产项目中，三者往往组合使用：

  1. 基础能力：用开源 RWKV-7 基底模型；
  2. 领域知识：用 RAG 接入私有知识库（成本低、更新快）；
  3. 风格/角色：用 State Tuning 或 LoRA 微调出想要的"性格"；
  4. 即时控制：用系统提示词做日常的"人设开关"。

这种"基底模型 + 检索 + 轻量微调"的架构，成本最低、效果最好、迭代最快，也是我们第十二章工程套用的主线。

11.8 微调避坑指南

坑 现象 解决办法
数据太少 微调后变"复读机" 数据量至少几百条；或改用 State Tuning
格式不对 训练崩/回答乱 严格按对话模板格式化
过拟合 只会背训练集 加正则、降学习率、增数据多样性
显存不足 OOM 用 LoRA / QLoRA / State Tuning
量化后变笨 回复质量下降 用 Q8_0 或更高精度微调/推理
**本章小结**：想让 RWKV 懂业务，三件套——RAG 管"知识"（外挂资料）、微调管"能力"（改权重）、State Tuning 管"个性"（改状态，RWKV 独有且又快又省）。推荐组合：基底模型 + RAG + 轻量微调/State Tuning + 提示词控制。

12.1 先看应用全景：RWKV 适合哪四类场景

在动手之前，先建立"RWKV 擅长什么"的全局观：

12.1.1 场景一：长会话 / 角色扮演 / 陪伴对话（核心）

  • 用户与 AI 长期、高频、多轮交流；
  • 需要"越聊越懂你"，且希望成本可控；

12.1.2 场景二：RAG 知识问答 / 智能客服

  • 要基于私有文档回答；

12.1.4 场景四：个性化微调 / 低成本定制

  • 让模型"变成某个性格/人设"；
  • State Tuning 让个性化几乎零成本。

12.2 我们的场景：AI 陪伴 / 情感智能体的痛点

假设我们正在做一个 AI 陪伴 / 情感智能体产品（比如"虚拟朋友、心理陪伴、角色扮演伙伴"）。它有几个非常典型的痛点：

痛点 具体表现 Transformer 的困境 RWKV 的解法
长会话成本高 用户每天聊几十轮，长期陪伴 KV Cache 越聊越贵，最终爆内存 状态固定，聊多久都便宜

结论：AI 陪伴 / 情感智能体，几乎就是为 RWKV 的优缺点量身定做的场景。

12.4 模块一：角色人设挂载（两种方式）

方式 A：提示词（最快）

你的说话风格：简短、温暖、先共情再建议。
你永远记得：用户需要的是被理解，而不是被说教。"""

方式 B：State Tuning（更"入戏"）

  • 用 RWKV-PEFT 对"小暖"风格的对话做 State Tuning；
  • 得到 .st 状态文件，推理时挂载；

让 AI 不只是"会聊天"，还能"察觉情绪"：

12.6 模块三：长期记忆 = 状态持久化

这是 RWKV 相对其他架构的"降维打击"：

# 每个用户一个状态文件 = 一份"专属人生记忆"
def get_memory(user_id):
    return load_state(f"memory_{user_id}.pkl")

def remember(user_id, new_state):
    save_state(new_state, f"memory_{user_id}.pkl")

# 使用
state = get_memory(user_id)
reply, state = pipeline.generate(prompt, state=state)
remember(user_id, state)   # 记忆自动"续上"

对比 Transformer 的做法：Transformer 通常要把全部历史消息重新喂进去（token 成本随记忆长度爆炸），或引入外部向量记忆库做检索；RWKV 直接把"记忆"压缩在状态里，随聊随存，几乎零额外成本。

  • TTS 语音：把回复文本交给 TTS（如 Edge-TTS、开源 TTS），输出语音；
  • 多模态：RWKV 官方支持多模态方向，未来可接入语音/视觉。

13.1 常见问题 FAQ

Q1：RWKV 是 RNN 还是 Transformer？

RNN 变体。 RWKV 推理时以循环方式工作（每步只带一份状态），但训练时又能像 Transformer 一样并行。它是"RNN 的身板 + Transformer 的训练效率"，但不含任何自注意力。

Q2：RWKV 会取代 Transformer 吗？

不会立刻取代，而是多一种选择。 在长对话、低资源、边缘、私有化场景，RWKV 性价比更高；在极致效果、成熟生态、极致长上下文精确回忆场景，Transformer 仍是主流。两者互补。

Q3：RWKV 的"无限上下文"是真的吗？

推理成本上接近无限（内存/速度不随长度暴涨），但记忆质量有上限——毕竟是压缩摘要，极长时会有信息损失。工程上建议"长上下文 + 分段总结/检索"配合。

Q4：RWKV 和 Mamba 有什么区别？

都属于"状态空间/线性注意力"家族，但实现不同：Mamba 用连续系统离散化 + 输入相关选择机制；RWKV 用显式可学习衰减（W）+ 感受态门控（R）+ Token Shift，且是 100% 无注意力、全系开源可跑。RWKV 的独特卖点还包括 State Tuning。

Q5：我的电脑能跑吗？

  • 8GB 内存：跑 1.5B / 2.9B 量化没问题；
  • 8GB 显存：可跑 2.9B fp16 或 7B 量化；
  • 只有 CPU：跑 1.5B 量化能聊天（约 5-10 tok/s）。

Q6：RWKV 商用要钱吗？

免费。 RWKV 模型、代码、内核均为 Apache 2.0 开源，属于 Linux 基金会项目，可自由使用、修改、商用。

Q7：为什么要开启官方 CUDA 内核？

RWKV-6/7 的数据相关衰减让并行计算变复杂，官方 WKV 内核能大幅提速。用 RWKV Pip / Albatross / vLLM 等方案会自动利用，建议保持开启。

Q8：RWKV 的多语言效果怎么样？

很好，且是强项。 RWKV-7 在 3B 规模多语言 benchmark 上刷新 SOTA，非英语语言尤其突出；RWKV-6 World 14B 覆盖大量语言。

Q9：我想让 RWKV 变成某个角色，最省的方法是什么？

State Tuning。 不动权重、只调状态，几乎零成本换"性格"，效果甚至比提示词更稳定，还能迁移复用。

Q10：RWKV 现在有哪些模型可以选？

模型 规模 特点
RWKV-7 G1 1.5B / 2.9B 最新，带思考模式，推荐
RWKV-7 World 1.5B / 2.9B 老版 World 系列
RWKV-6 World 7B / 14B 多语言，14B 最强
RWKV-6 / v4 系列 0.1B–7B 社区广泛使用

13.2 选型决策框架：我到底该不该用 RWKV？

用一个"打钩表"帮你快速决策：

判断问题 是 → 倾向
场景是长对话/多轮陪伴？ RWKV

第十四章 补课：文本是怎么变成数字的（Tokenizer 与数据流）

前面我们一直在说"token"，但可能有些小白还不清楚：AI 读的并不是文字，而是一串数字。 这一章专门补上这块拼图，讲清楚"文本 → token → 向量 → 模型 → 文本"的完整数据流，以及 RWKV 的 tokenizer 有什么特别之处。

14.1 为什么模型不能直接读文字

计算机里的神经网络只能处理数字，不能直接处理汉字、英文单词。所以我们要先把文字翻译成"模型能懂的数字表示"。这个过程分两步：

  1. Tokenize（分词）：把句子切成若干"词元（token）"；
  2. Embedding（向量化）：把每个 token 映射成一个高维数字向量。

模型拿到的是"一串向量"，处理完再反向解码成文字。

14.2 什么是 Token：最小处理单位

Token 是"模型处理文字的最小单位"。它可能是：

文本 可能的切分方式
一个汉字"爱" 1 个 token（中文常按字/词切）
"人工智能" 可能是 1 个 token（整词）或 4 个 token（逐字）
"hello" 可能是 1 个 token
"world" 1 个 token
"unbelievable" 可能切成 "un" + "believ" + "able" 多个 token
  • 词级切分：按空格/词切。缺点：词汇表巨大，且没见过的新词无法处理；
  • 字符级切分：按字母/字切。缺点：序列太长，效率低；
  • 子词切分（主流）：在"词"和"字"之间取平衡。常见的有 BPE（Byte Pair Encoding）、WordPiece、SentencePiece 等。

一个通用规律：英文大约 1 个单词 ≈ 1.3 个 token；中文大约 1 个汉字 ≈ 1~2 个 token。 这也解释了为什么"同样字数，中文模型的 token 开销往往更高"。

14.3 Tokenize 之后：Embedding（向量化）

切好 token 后，每个 token 会通过一张"查找表（embedding 表）"映射成一个固定维度的向量：

  • 比如维度 d=768 或 d=4096；
  • "爱" 和 "喜欢" 因为语义相近，它们的向量在高维空间里也会靠得比较近；
  • 这张表是模型训练时学出来的。

小白版：Token 是"字"，Embedding 是"这个字的含义坐标"。相似含义的词，坐标也相近。模型处理的就是这些"含义坐标"。

14.4 完整数据流：一段文字在模型里走一趟

用"我喜欢吃苹果"这句话举例：

步骤 发生了什么 数据形态
1. 原始文本 "我喜欢吃苹果" 字符串
2. Tokenize ["我","喜欢","吃","苹果"] 一串 token id（整数）
3. Embedding 每个 id 查表得向量 [4, d] 的矩阵
4. 模型前向 逐层计算，更新状态 S 隐藏状态 + 输出分布
5. 采样 按概率选下一个 token 一个 token id
6. Decode 把 id 查回文字 字符串
7. 循环 把新 token 接回输入，继续 直到结束

14.5 RWKV 的 Tokenizer 有什么特别

RWKV 使用社区自研的 tokenizer（如 rwkv_vocab_v304），并与 rwkv 库绑定使用。要点：

  • 与模型配套：加载模型时必须用配套的 tokenizer，否则会乱码（这是新手最常见的坑之一）；
  • 多语言友好：RWKV 的 tokenizer 对中文等多语言支持不错，这是它多语言表现好的基础之一；
  • 字节级覆盖：能处理各种 Unicode 字符（emoji、特殊符号等）。
# 用 rwkv 库时，tokenizer 已经内置在 pipeline 里
from rwkv.utils import PIPELINE
pipeline = PIPELINE(model, "rwkv_vocab_v304")  # tokenizer 名称

# 看看"文字 → token"长什么样
ids = pipeline.encode("我喜欢吃苹果")
print(ids)          # [t1, t2, t3, t4, ...] token 整数序列

# 看看"token → 文字"（解码）
text = pipeline.decode(ids)
print(text)         # 我喜欢吃苹果

14.6 为什么"上下文长度"是以 token 计的

所有大模型的"上下文长度"（context length）都是用 token 数来衡量的，而不是字数。因为模型真正"看过"的是 token 序列：

  • 一个模型的上下文是 4096 token，意味着它能"同时记住"最近约 4096 个 token 的内容；
  • 中文一句约 20 字 ≈ 20-40 token，所以 4096 token ≈ 一百多句中文；
  • RWKV 因为内存恒定，把上下文长度调大几乎不增加推理成本——这是它和 Transformer 的又一大区别（Transformer 上下文翻倍，KV Cache 也翻倍）。
# Ollama 里设置上下文长度
/set num_ctx 32768   # 例如把上下文调到 32K token

14.7 采样输出：模型如何"说下一个字"

模型前向计算的最后，会输出一个"下一个 token 的概率分布"——对词汇表里每个 token 都给出一个概率（比如"苹"40%、"火"30%、"鸡"20%……）。然后：

  • 贪心采样：永远选概率最高的那个 → 稳定但死板；
  • 温度采样：把概率分布"压扁"或"拉尖"后采样 → 温度越高越随机；
  • Top-P / Top-K：先砍掉概率太低的候选，再采样 → 避免选到离谱的 token。

这就是第九章讲的参数（temperature/top_p）发挥作用的地方。

14.8 新手常见问题

问题 原因 解决
输出全是乱码/问号 tokenizer 与模型不匹配 用配套 tokenizer
英文很好、中文很怪 tokenizer 中文覆盖率低 换多语言 tokenizer / World 模型
生成的文字超长不停止 没设 max_tokens 或没触发 EOS 设置 max_tokens、增加停止词
输入被截断 超过上下文长度 调大 num_ctx，或分段处理
**本章小结**：AI 读的是数字不是文字。流程 = 文本 → tokenize 成 token → embedding 成向量 → 模型前向（更新状态 S）→ 采样 → decode 回文字，循环生成。RWKV 的 tokenizer 需与模型配套，中文约占 1-2 token/字，且上下文长度以 token 计。

第十五章 它是怎么被训练出来的：训练原理与实战

"部署 + 使用"讲完了，这一章回答一个更底层的问题：RWKV 是怎么被训练出来的？ 理解了训练原理，你就明白为什么"双模式"如此巧妙，也知道了以后想自己训练/微调时该做什么。

15.1 训练的目标：预测下一个词

大语言模型的训练目标朴素得惊人：给定前面的文字，预测下一个词。 这叫"自监督学习"——不需要人工标注，互联网上的海量文本本身就是"答案"。

  • 给模型看"今天天气真"，让它预测下一个词"好"；
  • 看"我喜欢吃"，预测"苹果/火锅/香蕉……"；
  • 看完几万亿 token 之后，模型就"内化"了语言规律和大量世界知识。

这个任务叫 next-token prediction（下一个词预测），是所有 GPT 系模型（包括 RWKV）的基础。

15.2 双模式是怎么在训练中工作的

回忆第五章：RWKV 同一套权重有"GPT 模式（并行）"和"RNN 模式（循环）"两种跑法。训练时用 GPT 模式，推理时用 RNN 模式：

训练（GPT 模式） 推理（RNN 模式）
处理方式 整段序列一次摊开并行算 一个 token 一个 token 串行走
计算对象 一次算出所有位置的输出 每步只算当前 token 的输出
状态处理 用"前缀和"技巧一次性模拟 显式维护一个状态 S
为什么能 WKV 可分解（衰减与输入无关时可并行） 状态式 RNN 天然支持

核心洞察：训练时的"并行"不需要真的一个个更新状态——因为 WKV 的衰减结构可以写成前缀和（cumulative sum），整条时间轴一次性并行算出。这就是"RNN 居然能并行训练"的秘密。

15.3 损失函数与反向传播

训练时，模型每个位置都会输出一个预测分布，我们要让它和"真实的下一个词"尽量一致：

  • 用交叉熵损失（cross-entropy）衡量"预测得有多不准"；
  • 误差通过反向传播（backpropagation）更新模型参数；
  • 训练数据按 batch（一批一批） 喂给模型，用 梯度下降 逐步优化。

小白版：模型猜错了 → 告诉它"正确答案是啥" → 它调整自己的参数，下次更接近 → 反复几万亿次，就变聪明了。

15.4 RWKV 训练的三个特点

15.4.1 特点一：训练显存更低

Transformer 训练时要保存大量中间激活（每层、每个 token 的注意力分数等）用于反向传播；RWKV 因为状态式结构，中间量更少，训练/微调的显存占用明显更低。这让你"单卡微调"成为可能。

15.4.2 特点二：天然适合长序列训练

长序列训练对 Transformer 是噩梦（显存随长度平方涨，需要各种分片技巧）；RWKV 是线性，训练长上下文更省。

15.4.3 特点三：需要专用内核加速

v6/v7 引入了"数据相关衰减"后，WKV 不能再简单写成前缀和，并行实现变复杂。官方提供专用 CUDA 内核（WKV kernel）高效实现，训练和推理都应尽量开启。

# RWKV-LM 训练脚本里，用 --cuda_on 或 strategy 开启官方内核
# 例如用 RWKV-LM 的 train.py：
# python train.py --load_model ... --wandb ... --ctx_len 4096 ...

15.5 训练的三个阶段

阶段 做什么 数据 目的
预训练（Pretrain） 从零学语言规律和世界知识 海量网页/书籍（万亿 token） 让模型"会说话、懂知识"
指令微调（SFT） 学会"听指令回答问题" 人工编写的问答数据 让模型"能对话、会干活"
对齐（RLHF 等） 让回答更符合人类偏好 人类反馈打分 让模型"更友善、更有用"

RWKV 的开源模型（如 RWKV-6 World、RWKV-7 G1）都已完成了这三个阶段，开箱即用。我们自己动手时，通常做的是指令微调或State Tuning（见第十一章）。

15.6 从零训练 vs 微调：成本和选择

方式 数据量 算力 时间成本 适合谁
从零预训练 万亿级 token 大量 GPU 集群 极高 大厂/研究机构

对绝大多数人：不要从零训练，用开源的 RWKV + 轻量微调/State Tuning 就够了。

15.7 一个迷你训练示例（示意）

以 RWKV-LM 仓库的训练脚本为例，理解训练入口大概长什么样（不必真跑）：

  --wandb off \

要点：

无论预训练还是微调，数据质量都决定效果：

**本章小结**：RWKV 的训练目标就是"预测下一个词"。训练用 GPT 模式（靠 WKV 可分解性并行），推理用 RNN 模式。三大特点：显存低、适合长序列、需专用内核。对绝大多数人，直接使用开源模型 + 轻量微调（LoRA/State Tuning）即可，无需从零训练。

第十六章 量化与性能优化：把 RWKV 压榨到极限

RWKV 已经很"省"了，但还能更省。这一章讲清楚量化是什么、怎么选，以及各种提速/省内存的实用技巧，让你在有限的硬件上发挥 RWKV 的最大威力。

16.1 什么是量化：用更小的数存模型

模型权重默认用 32 位浮点数（FP32）或 16 位（FP16）存储，占用空间大。量化就是把这些"大数"用更小的精度表示，从而显著减少内存、加快速度。

精度 每参数比特 7B 模型体积（约） 效果
FP32 32 bit 28 GB 最准，最贵
FP16 16 bit 14 GB 精度无损，常用
INT8（Q8_0） 8 bit 7 GB 精度损失小，强烈推荐
INT4（Q4_K_M 等） 4 bit 4 GB 更省，质量略降
NF4 / Q3 3-4 bit 3 GB 极致省，质量下降明显

RWKV 的量化建议：社区实测推荐 FP16 或 Q8_0 档。更低的 Q5/Q4 虽能大幅省内存，但会明显降低回复质量——"够用"和"好用"之间要权衡。

16.3.1 技巧一：开启官方 WKV 内核

这是最重要的一条。RWKV-6/7 的数据相关衰减需要专用 CUDA/ROCm 内核才能高效并行：

  • 用 RWKV Pip：NVIDIA 显卡选 cuda fp16，显存不足用 cuda fp16i8；

  • 用 vLLM：自动启用优化内核。

很多"RWKV 很慢"的反馈，都是因为没开官方内核、在 CPU 上裸跑导致的。

16.3.5 技巧五：批量推理 / 服务化

生产场景用 vLLM 的 continuous batching（连续批处理），把多个请求拼在一起算，GPU 利用率大幅提升，吞吐翻数倍。

  1. 首 token 延迟（TTFT）：问完到开始回答的时间；
  2. 生成速度（tok/s）：每秒生成多少 token；
  3. 显存/内存峰值：是否恒定、是否够用。

第十七章 公式通俗课：RWKV 的数学只讲直觉

很多教程一上来就甩公式，小白直接劝退。这一章反着来：只讲公式背后的直觉，把 RWKV 的核心数学用"买菜、记账、做笔记"的比喻讲清楚。你不需要会推导，只需要"看懂它想干什么"。

17.1 预备：向量、矩阵、点积，用生活语言理解

  • 向量：一列数字，可以理解成"一个东西在多维空间的坐标"。比如"苹果"可以用 [甜度, 价格, 热量, ...] 表示；
  • 矩阵：一堆向量排成表格；
  • 点积（内积）：两个向量对应位置相乘再求和。直觉：衡量两个向量有多"相似/对齐"。方向一致 → 点积大；方向垂直 → 点积为 0。

记住"点积 = 相似度打分"，RWKV 的数学就通了一半。

17.2 四个字母的数学直觉（R / W / K / V）

字母 数学角色 生活直觉 通俗公式
R 感受态（门控系数） "这条信息我接受多少" R 乘在最终结果上
W 衰减系数 "记忆忘得多快" 越旧乘越小的系数
K 键 "这条信息叫什么名字" 用于"对号入座"
V 值 "这条信息的实际内容" 真正被记住的内容

17.3 WKV 算子：三句话讲清核心公式

RWKV-4 的经典 WKV 公式（不背，只看结构）：

output_t = R_t · (  Σ_{i<t}  exp(-w·(t-i)) · (K_i · V_i)  +  exp(u)·(K_t · V_t) )

拆成三句话：

  1. K_i · V_i（写入）：每个历史词把"名字 × 内容"记进状态——就像记账时写下"日期 × 金额"；
  2. exp(-w·(t-i))（衰减）：越早的账目乘的衰减系数越小——就像老账目被时间冲淡；
  3. R_t（读出/门控）：当前这个词决定"这段记忆对我重不重要"——就像翻账本时只挑有关的看。

一句话：WKV = 把历史"按新旧打折后求和"，再乘一个"要不要管它"的开关。

17.4 为什么是"指数衰减"而不是"直接忘掉"

  • 指数衰减：exp(-w·(t-i)) 让旧信息平滑地、按比例地变淡，但不会瞬间归零——远亲也能沾点光；
  • 对比 RNN 的"梯度消失"（失控地忘）：RWKV 的衰减是显式、可学习的（W 是训练出来的参数），所以模型能自己决定"该记多久"。

这正是 RWKV "不健忘"的秘密：把"遗忘"从玄学变成可调的旋钮。

17.5 Token Shift 的数学

Shift(x[t]) = μ · x[t] + (1 - μ) · x[t-1]
  • 就是"当前值"和"上一个值"按比例混合；
  • μ 是混合比例（不同通道可以不同）；
  • 效果：每个 token "自带一点上一时刻的影子"，补充邻近信息。

为什么叫"短卷积"：它等价于一个核长 2 的卷积，几乎零成本，却能显著提升表现——RWKV 的"以小博大"典型例子。

17.6 Channel Mixing 的数学

out = sigmoid(R) ⊙ ( W2 · gelu(W1 · K) ) ⊙ V

逐块拆解：

符号 含义 直觉
W1 · K 线性变换 把输入换个"视角"看
gelu(...) 非线性激活 引入非线性，增强表达
W2 · ... 再变换 加工后回到原维度
sigmoid(R) 门控 决定"这些特征要不要激活"
⊙ 逐元素相乘 逐位把关

一句话：Channel Mixing 就是在"同一个时刻"上，把特征加工得更丰富，再按需放行——作用类似 Transformer 的 FFN。

17.7 RWKV-7：动态状态演化（广义 Delta 规则）

RWKV-7 的状态更新比 v4 复杂，但直觉更简单——会改错：

旧版（v4）： S = 衰减 · S + K·V        # 只能写，不能改
新版（v7）： S = S · 门控 + 基于误差的修正   # 能写，还能改

用"做笔记"比喻：

  • v4：一边读一边记，但记错了就一直错下去；
  • v7：读完一段会"对答案"，发现记错了就修正笔记——所以记性更好、更会"状态追踪"。

这正是论文里说的"元上下文学习器"：模型在每个 token 上，用"上下文里的梯度下降"自我调整状态。

17.8 复杂度的数学：为什么差一个 N

  • Transformer：N 个词两两打分 → 需要 N×N 次 → O(N²)；
  • RWKV：每个词只更新一次固定状态 → 需要 N 次 → O(N)。
O(N²)  vs  O(N)
N=4K：1600万  vs  4000
N=32K：10亿    vs  3.2万

这就是"长上下文不心疼"的全部秘密——少算了一个 N 的配对。

17.9 一张"公式 → 直觉"对照表

公式/术语 数学形式 生活直觉
点积 K·V Σ K_i·V_i 记下"名字×内容"
指数衰减 exp(-w·(t-i)) 老账按比例冲淡
感受态 R sigmoid(R) 开关：要不要管它
Token Shift μ·x[t]+(1-μ)·x[t-1] 瞥一眼上一句
归一化分母 /Σ exp(-w·(t-i)) 让账本总和不发散
Delta 规则（v7） S←S·D+误差修正 记错了就改
前缀和并行 cumsum 摊开来一次算完
**本章小结**：RWKV 的核心数学只有三招——**点积写记忆、指数衰减忘记忆、感受态门控读记忆**。v7 加了一招"能改错"。复杂度的差距来自"少算一个 N"。记住这些直觉，公式就不再吓人了。

第十八章 高效架构家族：RWKV vs Mamba vs RetNet

RWKV 并不孤单。在"用状态代替注意力"这条路上，还有 Mamba、RetNet、Gated DeltaNet 等一批高效架构。这一章帮你建立全局观：它们各自怎么"省"、差异在哪、RWKV 的位置和优势是什么。

18.1 为什么大家都在"去注意力"

Transformer 的 O(N²) 是行业痛点，于是出现了一整条研究路线：用"固定大小的状态/记忆"替代"两两配对的注意力"，把复杂度降到 O(N) 甚至 O(1)。这些架构统称"线性注意力 / 状态空间 / 高效序列模型"。

18.2 逐个认识家族成员

18.2.1 Mamba（SSM 派）

  • 思想：来自控制论的状态空间模型（SSM），把序列建模看成"连续系统 + 离散采样"；
  • 关键机制：选择性扫描（selective scan）——每个位置决定"吸收多少新信息"；
  • 特点：训练可用并行扫描，推理是常数开销；在某些长序列任务上表现出色。

18.2.2 RetNet（微软）

  • 思想：显式引入衰减（decay），用"线性注意力 + 衰减"模拟位置效应；
  • 特点：提出三种并行模式，推理也可常数开销；和 RWKV 思路较接近（都有显式衰减）。

18.2.3 Gated DeltaNet

  • 思想：把 Delta 规则引入状态更新——让状态能"修正"而不是只能"累积"；
  • 特点：和 RWKV-7 的 DSE 思想一脉相承（都强调"可更新的记忆"）。

18.2.4 RWKV

  • 思想：R / W / K / V 四件套——感受态门控 + 显式可学衰减 + 键值写入 + 值读出；
  • 特点：100% 无注意力、训练并行 + 推理常数、有 State Tuning 独家能力、从 0.1B 到 7.2B 全系开源可商用。

18.3 一张表对比全家

架构 记忆机制 复杂度 训练并行 推理成本 代表模型
Transformer 自注意力 + KV Cache O(N²) 完全并行 随上下文增长 GPT/Llama/Qwen
Mamba SSM 状态 + 选择机制 O(N) 并行扫描 常数 Mamba-1/2
RetNet 线性注意力 + 显式衰减 O(N) 并行 常数 RetNet

18.4 RWKV 的差异化优势

和同族相比，RWKV 有几个"别人没有"的特点：

18.5 和其他架构的常见误区澄清

误区一："RWKV 就是 Mamba"

不是。 虽然都属于"线性注意力/状态"家族，但机制不同：Mamba 来自 SSM（连续系统离散化），RWKV 来自 RNN + 显式衰减 + Token Shift。RWKV 强调"R/W/K/V 四件套 + 可学衰减"，Mamba 强调"选择性扫描"。

误区二："高效架构效果都不如 Transformer"

分任务。 在标准 benchmark 上，头部高效架构（含 RWKV-7）已能与同规模 Transformer 打平甚至超过；在"状态追踪"等特定推理任务上，RWKV-7 理论上还能超过注意力受限的模型。真正有差距的是"超大模型规模下的极致效果"和"生态成熟度"。

误区三："线性注意力都有严重记忆损失"

旧版确实有，但已改善。 RWKV-7 的动态状态演化让状态可修正，大幅缓解了记忆"只进不出"的问题；不过对"逐字精确回忆"仍弱于完整注意力，因此出现了 RWKV-X 等"状态 + 稀疏注意力"的混合方案。

18.6 混合架构趋势：RWKV-X

最近的一个方向是混合架构：以状态记忆为主干，在关键位置混入少量稀疏注意力，兼顾"便宜"和"精确回忆"：

  • RWKV-X：RWKV + 稀疏注意力，补强极端细节回忆；
  • RWKV-8 DeepEmbedAttention：精简 KV Cache，特别适合混合模型；
  • 类似趋势：很多大厂也在做"线性 + 稀疏"混合，这可能是未来主流形态。

判断：纯 RNN 派（RWKV）、SSM 派（Mamba）、混合派（RWKV-X / 各类 linear-attention hybrid）会长期共存，各取所长。

RWKV 不只是文本模型。这一章看看它的多模态能力、最新实验方向（v8、混合架构），以及"未来 RWKV 会往哪走"，帮你判断要不要长期押注它。

19.2.3 ROSA（在线后缀自动机机制）

  • 目标：更强的记忆与检索能力；
  • 名字来自"在线后缀自动机"，本质是让记忆可以更灵活地被索引和回溯；
  • 意义：进一步补强"精确回忆"，缩小与注意力的差距。

19.3 混合架构：未来最可能的形态

  • RWKV-X：RWKV + 稀疏注意力，已出现；

判断：未来的 RWKV 大概率不是"纯 RNN"，而是"以状态为主、混合稀疏注意力"的进化版——既保留便宜，又补强精确。

第二十一章 提示词工程实战：让 RWKV 更听话

"模型强不强"一半看模型，一半看你怎么问。这一章专门讲 RWKV 的提示词（Prompt）工程技巧——从基础结构到 RWKV 的专属玩法，让你花最小的成本，把模型效果榨到最好。

21.1 一条好提示词的四大要素

一个完整、有效的提示词通常包含：

要素 作用 示例
角色（Role） 设定身份与立场 "你是一名温柔的心理咨询师"
任务（Task） 明确要干什么 "请概括这段文字"
约束（Constraints） 限定格式/风格/边界 "用 100 字以内，分三点"
示例（Examples） 给一个标准答案样板 "例如：……"

黄金结构：角色 + 任务 + 约束 + 示例。四件套齐全，输出质量明显上升。

21.2 角色设定：RWKV 很吃这一套

RWKV 这类模型对"角色"非常敏感。同一个问题，加不加角色，效果天差地别：

✗ 差：解释一下什么是焦虑。
✓ 好：你是一位有 10 年经验的心理咨询师。请用温柔、通俗的语言，向一位 20 岁的年轻人解释什么是焦虑，并给出 3 条缓解建议。

角色越具体，输出越"入戏"、越稳定。这对我们后面做 AI 陪伴（第十二章）尤其重要。

21.3 格式约束：让输出"可控"

想让输出变成 JSON、列表、表格，直接说清楚：

请分析下面这段话的情绪，只输出 JSON：
{"emotion": "<开心/平静/难过/焦虑/愤怒/疲惫>", "confidence": <0~1>}

文本：今天工作被领导骂了，好烦。

输出：

{"emotion": "焦虑", "confidence": 0.85}

技巧：明确给出"输出格式模板"，比只说"结构化输出"有效得多。

21.4 少样本（Few-shot）：给几个例子胜过千言万语

给模型 1-3 个"输入 → 输出"示例，它就能模仿你的格式和风格：

把口语转成书面语：

口语：那啥，明儿咱们去逛个街呗？
书面语：明天我们一起去逛街，好吗？

口语：这事儿我觉得吧，其实也没啥大不了的。
书面语：我认为这件事其实并不严重。

口语：你等会儿，我马上来。
书面语：

模型会自动顺着你的"例子风格"继续，产出高度一致。

21.5 RWKV 专属提示词技巧

21.5.1 技巧一：状态式思考，善用"记忆"

RWKV 有状态记忆，多轮对话时不需要把历史再抄一遍。系统提示词里放"长期人设"，每轮只放"本轮增量"：

# 系统提示词（只设一次）
你是小暖，温柔耐心的 AI 伙伴。你记得用户的喜好和过往。

# 每轮只传当前消息（状态自动带着记忆）
用户：我今天有点难过……

这比 Transformer 的"每轮把整段历史重发"更省、更自然。

21.5.2 技巧二：用 State Tuning 固化人设

如果提示词太长（占大量 token），或者人设总是不稳定，就该上 State Tuning 了：把人设"训练进状态"，提示词就可以大大缩短，甚至只留一句"你是小暖"。

21.5.3 技巧三：善用"思考模式"开关

RWKV-7 G1 默认带思考模式（/set think / /set nothink）：

  • 要严谨回答（数学、代码、推理）→ 开思考模式；
  • 要快速闲聊（陪伴、接话）→ 关思考模式，更快更省。

21.5.4 技巧四：重复惩罚对抗"车轱辘话"

陪伴类对话里模型容易重复，除了调 repetition_penalty，提示词里也可以写：

请避免重复用词和句式，不要复读之前说过的话。

21.6 常见提示词误区

误区 表现 改正
提示词太短 输出泛泛而谈 补上角色 + 约束 + 示例
要求太多 顾此失彼 一次只聚焦 1-2 个要求
措辞模糊 输出跑偏 用"具体"代替"大概"
提示词超长 占上下文、易被稀释 精简，或转 State Tuning
忘记约束输出格式 解析困难 给出明确格式模板

21.7 提示词模板库（直接抄）

模板一：通用助手

你是一个友好、专业的中文 AI 助手。请直接、简洁地回答问题，不要啰嗦。
问题：{问题}

模板二：总结提炼

请把下面这段文字概括为 {N} 个要点，每个要点不超过 {M} 字，用编号列表输出：
{文本}

模板三：角色扮演 / 陪伴

你是 {角色名}，性格 {性格描述}。说话风格：{风格}。
规则：先共情，再回应；不要长篇大论说教。
用户说：{消息}

模板四：结构化抽取

从下面文本中抽取 {字段列表}，输出 JSON：
{文本}

21.8 提示词调优流程（方法论）

  1. 先写出基线提示词（角色+任务+约束+示例）；
  2. 跑 5-10 个测试用例，记录失败点；
  3. 定位问题：是缺角色？缺示例？还是约束不清晰？
  4. 针对性修改，一次只改一处；
  5. 回归测试，确认没改坏其他用例；
  6. 反复迭代，直到稳定。

提示词工程是"低成本迭代"：不用重新训练，几行字就能显著提升效果。先把它做到极致，再考虑微调/State Tuning。

**本章小结**：提示词 = 角色 + 任务 + 约束 + 示例。RWKV 的专属技巧：状态式思考（少传历史）、State Tuning 固化人设、思考模式开关、重复惩罚。先做提示词优化（零成本），不够再上微调。

第二十二章 真实案例巡礼：别人怎么用 RWKV

看别人怎么把 RWKV 用起来，是最快的学习方式。这一章盘点 RWKV 在真实世界的典型用法——从代码补全到智能客服，从陪伴机器人到边缘设备，帮你打开"我还能拿它做什么"的思路。

22.1 案例一：VS Code 代码补全插件

社区有人基于 RWKV 做了一个 VS Code 代码补全插件（rwkv-code-completion）：

  • 原理：用 RWKV 的续写/FIM（Fill-in-the-Middle）能力，在光标处预测代码；
  • 亮点：并发推理一次返回多个候选补全，侧边栏展示、点选插入；
  • 技术栈：前端 VS Code 扩展 + 后端 rwkv_lightning（HTTP API）；
  • 为什么用 RWKV：本地跑、低显存、补全延迟稳定，隐私好（代码不出本地）。

启示：RWKV 的"低资源本地推理"特性，特别适合 IDE 这类"要快、要隐私、要常驻"的场景。

22.2 案例二：私有化智能客服 / 知识问答

用 RAG 方案（第十一章）给企业做"私有知识库问答"：

  • 流程：文档入库 → 向量化 → 检索 → 注入 → RWKV 生成；
  • 为什么用 RWKV：数据不出本地（合规）、长上下文（能塞多段资料）、显存恒定；
  • 典型形态：企业内部"员工手册问答""产品客服""法律/财务文档助手"。

22.3 案例三：AI 陪伴 / 角色扮演 / 情感支持

这是 RWKV 最"量身定做"的场景（也是我们第十二章的重点）：

  • 产品形态：虚拟朋友、心理陪伴、角色扮演伙伴；
  • 核心能力：状态持久化（记得用户）、恒定内存（长会话不崩）、State Tuning（低成本换人设）；
  • 工程组合：人设提示词 / State + 情绪检测 + 状态存档 + TTS 语音。

22.4 案例四：边缘设备 / 离线部署

在树莓派、旧笔记本、无网环境跑 RWKV：

  • 形态：量化 GGUF + llama.cpp，8GB 内存跑 2.9B；
  • 场景：车载语音助手、离线翻译、智能家居、野外作业设备；
  • 为什么用 RWKV：CPU 可跑、内存恒定、离线可用、隐私安全。

22.5 案例五：长文档处理 / 智能写作

利用 RWKV 的"长上下文免费"优势：

  • 长文档总结：把整本书/整份合同塞进去总结；
  • 论文/报告辅助：读长资料后按要求输出；
  • 剧本/小说续写：上下文越长，剧情连贯性越好；
  • 多文档对比：同时塞入多份资料做对比分析。

22.6 案例六：低成本多语言应用

RWKV-6 World 14B 覆盖大量语言，且多语言效果好：

  • 翻译工具：本地翻译，无 API 费用；
  • 多语言客服：一套模型服务多语言用户；
  • 低资源语言助手：对小语种更友好。

24.1 从 Demo 到生产：差距在哪里

核心思路：RWKV 最大的工程红利是"状态（State）"。Transformer 产品要缓存一整套 KV 历史才能续聊，RWKV 只需要持久化一份固定大小的状态文件——这会让你的存储和续聊逻辑简单一个数量级。

形态一：单机轻服务（个人/小团队）

  • 适用：内网工具、个人 AI 助手、小流量陪伴应用。

  • 适用：面向公众的聊天产品、多租户 SaaS。

形态三：混合架构（大模型 + 小模型/规则）

  • 80% 简单请求走 RWKV 小模型（1.5B/2.9B 量化），省成本；

24.3 状态管理：RWKV 的"杀手级工程实践"

这是 RWKV 相对 Transformer 最独特、最值得利用的工程点。核心模式是"状态即身份"：

from rwkv.model import RWKV
from rwkv.utils import PIPELINE

model = RWKV(model="/path/rwkv-7.pth", strategy="cuda fp16")
pipe = PIPELINE(model, "rwkv_vocab_v20230424")

def new_session(role_id):
    """每个角色/用户一个独立状态"""
    return {"role": role_id, "state": None, "history": []}

def chat(sess, text):
    out, sess["state"] = model.run([text], sess["state"])  # 传旧状态、收新状态
    sess["history"].append(text)
    return out

生产落地的三个要点：

  1. 状态持久化到数据库：把 state 序列化存进 Redis / 数据库，用户下次进来直接读回，实现"跨会话不失忆"——而 Transformer 想做同样的事，要存整段 KV Cache，代价大得多。
  2. 多用户隔离：每个用户一份状态，天然隔离，互不串台；这比"把所有上下文拼一起再丢给模型"干净得多。
  3. 状态归档与分片：一个角色一个文件/一个 key；长对话可用"总结压缩"定期把旧状态精简。

为什么这对你的产品重要：AI 陪伴/情感智能体的核心卖点就是"它记得我"。用 RWKV，这个记忆是"一等公民"（一份文件的事），实现成本远低于 Transformer 路线。

25.1 架构演进的下一站

RWKV 的演进有一条清晰的脉络：每次迭代都在解决"状态的表达能力"问题。

版本 状态机制 解决的核心问题
v1–v4 固定衰减（W 不可随输入变化） 证明"无注意力也能训练出模型"
v5/v6 数据相关衰减（W 随输入变化） 让遗忘系数"懂上下文"
v7（Goose） DSE 动态状态演化（可修正的线性注意力） 状态能"纠错"，逼近 Transformer 记忆精度
v8+ 实验阶段，探索更强的状态表达 进一步缩小与全注意力的差距

趋势判断（基于公开信息）：

  1. 混合化：RWKV-X 等实验表明，业界在探索"状态模型 + 少量注意力"的混合架构——用线性注意力扛长序列，用少量局部注意力补精确回忆。这可能不是"RWKV 输给 Transformer"，而是两个家族走向融合。
  2. 更大的多模态：语言 → 视觉 → 音频 → 世界模型。RWKV 的恒定内存特性，让"长视频/长音频流式理解"这种高耗场景反而成为它的优势场。
  3. 更强的状态机制：状态不再只是"摘要"，而是可读写、可纠错、可编辑的"外部记忆"，配合 State Tuning，可能催生"记忆即产品"的新范式。

25.2 这个方向会"赢"吗？理性看待

给你一副冷静的眼镜，别被任何一方带节奏：

论点 正（看好 RWKV 方向） 反（谨慎）
长上下文 恒定内存，成本可控 精确回忆仍不如全注意力
效率 O(N) 天生优势 硬件针对 Transformer 优化更多
生态 全系开源、Apache 2.0 工具链、生态规模小于 Transformer
科研 理论清晰（TC0 类） 头部算力仍倾斜 Transformer

理性的结论：不是"谁取代谁"，而是任务决定架构——需要极长上下文、低资源、私有化、个性化、流式处理的任务，RWKV 这类线性注意力/状态模型会越来越有竞争力；需要极致效果和成熟生态的任务，Transformer 继续占主导。两者共存，且越来越融合，这才是最可能的中期图景。

26.3 第一步：加载模型与基础对话

写一个最基础的 llm.py，把模型封装成"说一句话 → 返回回复"的接口：

# llm.py —— RWKV 推理封装
from rwkv.model import RWKV
from rwkv.utils import PIPELINE

MODEL_PATH = "./models/rwkv-7/rwkv-7.pth"
VOCAB_PATH = "./models/rwkv-7/rwkv_vocab_v20230424.txt"

# strategy: "cuda fp16" 用显卡；"cpu fp32" 没显卡也能跑
model = RWKV(model=MODEL_PATH, strategy="cuda fp16 * -> cuda fp16")
pipe = PIPELINE(model, VOCAB_PATH)

def generate(prompt: str, state=None, temperature=0.8):
    """返回 (回复文本, 新状态)"""
    # RWKV 官方库：把整段 prompt 一次性灌入，得到输出和最终状态
    out, state = model.run([prompt], state)
    return out, state

if __name__ == "__main__":
    text, st = generate("你好，我是谁？")
    print("助手:", text)

注意：官方 rwkv 库的 model.run 输入通常是"token 序列"。不同版本 API 略有差异，请以你安装版本的 README 为准；核心逻辑不变——每次调用都传回上一次的 state，实现连续记忆。

26.4 第二步：角色设定（System Prompt）

角色不是一个"开关"，而是写进每一轮输入开头的"身份卡"。我们把角色设定做成可配置：

# prompt.py —— 角色与对话模板
ROLE_CARD = """你叫 Memo，是一个温柔、耐心的倾听型 AI 朋友。
你说话简短、口语化，经常关心对方的感受。
如果对方提到难过的事，先共情，再给建议。
你永远使用简体中文回复。"""

def build_prompt(user_input: str, history: list[str]) -> str:
    """history 是最近几轮的短记忆，状态文件管长记忆"""
    chat = "\n".join(history[-6:])          # 只保留最近 6 条，防爆 token
    return f"{ROLE_CARD}\n\n最近的对话：\n{chat}\n用户：{user_input}\nMemo："

为什么这样设计：RWKV 的"状态"负责长期记忆（跨会话、记大事）；显式塞进 prompt 的 history 负责短期上下文（让回复更连贯）。两者分工，这是 RWKV 应用最舒服的用法。

26.5 第三步：把记忆做成"数据库"

这是本项目最 RWKV 的部分——状态即记忆，存进数据库：

# memory.py —— 用 SQLite 存状态，实现跨会话记忆
import sqlite3, pickle

DB = "memo.db"

def _conn():
    c = sqlite3.connect(DB)
    c.execute("CREATE TABLE IF NOT EXISTS sessions "
              "(uid TEXT PRIMARY KEY, state BLOB, history TEXT)")
    return c

def save_session(uid: str, state, history: list[str]):
    c = _conn()
    c.execute("INSERT OR REPLACE INTO sessions VALUES (?,?,?)",
              (uid, pickle.dumps(state), "\n".join(history)))
    c.commit(); c.close()

def load_session(uid: str):
    c = _conn()
    row = c.execute("SELECT state, history FROM sessions WHERE uid=?", (uid,)).fetchone()
    c.close()
    if not row:
        return None, []
    return pickle.loads(row[0]), row[1].split("\n")

工作原理：用户每说一句话，我们拿到新的 state，立刻存库。下次用户再来，直接读回 state——RWKV 就"还记得"之前的所有对话。整个过程不需要存任何原始长文本，一个状态文件搞定。

26.6 第四步：接入 FastAPI，做成 Web 服务

# app.py —— FastAPI 聊天接口
from fastapi import FastAPI
from pydantic import BaseModel
from llm import generate
from prompt import build_prompt
from memory import load_session, save_session

app = FastAPI()

class ChatIn(BaseModel):
    uid: str
    text: str

@app.post("/chat")
def chat(body: ChatIn):
    state, history = load_session(body.uid)          # 1. 读回记忆
    prompt = build_prompt(body.text, history)        # 2. 组 prompt
    reply, new_state = generate(prompt, state)       # 3. 生成回复
    save_session(body.uid, new_state, history + [body.text, reply])  # 4. 存记忆
    return {"reply": reply}

# 启动：uvicorn app:app --port 8000

26.8 第六步（可选）：接入本地知识库（RAG）

想让 Memo 能回答你资料里的问题？给它加一个"外挂知识库"：

# rag.py —— 极简 RAG：关键词 + 向量混合检索
# 这里用最朴素的实现演示思想；生产可换 FAISS / Chroma / Milvus
import hashlib, sqlite3

def add_doc(text: str):
    """把一段资料按句切分后入库"""
    for sentence in text.replace("\n", "。").split("。"):
        if len(sentence.strip()) > 10:
            conn = sqlite3.connect("kb.db")
            conn.execute("CREATE TABLE IF NOT EXISTS docs "
                         "(id TEXT PRIMARY KEY, content TEXT)")
            h = hashlib.md5(sentence.encode()).hexdigest()
            conn.execute("INSERT OR REPLACE INTO docs VALUES (?,?)", (h, sentence))
            conn.commit(); conn.close()

def search(query: str, topk: int = 3) -> str:
    """按关键词命中程度检索最相关的句子"""
    conn = sqlite3.connect("kb.db")
    rows = conn.execute("SELECT content FROM docs").fetchall()
    conn.close()
    q = set(query)
    scored = sorted(rows, key=lambda r: -len(q & set(r[0])))
    return "\n".join(c for c, *_ in scored[:topk])

然后改一下 build_prompt，把检索结果作为"参考资料"喂给模型：

def build_prompt(user_input, history):
    ref = search(user_input)          # 知识库检索结果
    return (f"{ROLE_CARD}\n\n参考资料：\n{ref}\n"
            f"（资料若无用请忽略）\n\n最近的对话：\n{history[-6:]}\n"
            f"用户：{user_input}\nMemo：")

效果：现在 Memo 既能"记住你"（状态），又能"查资料"（RAG），还"有人设"（角色卡）。一个三合一的小助手就完成了。

第二十七章 常见报错与排查手册

动手过程中，报错是常态，别慌。这一章把 RWKV 从部署到运行最常见的报错整理成"症状 → 原因 → 解法"的速查手册。遇到问题先来这里翻，能省下大量瞎折腾的时间。

27.1 通用排查方法论

在逐条查错之前，先记住一套"通用排查四步法"——它能解决八成问题：

  1. 看完整报错：报错最后几行才是关键（Traceback / Error 之后的正文）。别只看开头。
  2. 搜一下：把报错原文（英文部分）复制到搜索引擎 / rwkv.cn / Discord，十有八九有人踩过。
  3. 缩小范围：用"最小复现"测试——只跑最简命令，把环境、模型、代码变量逐个排除。
  4. 看版本：rwkv / torch / llama.cpp / ollama 版本不匹配是高频元凶，先统一版本。

通用环境诊断命令：

python -c "import torch; print(torch.__version__, torch.cuda.is_available())"
ollama list && ollama --version
nvidia-smi            # 看显存是否够
free -h               # 看内存是否够

症状 常见原因 解法

27.4 推理质量类"报错"（不算报错，但很常见）

症状 常见原因 解法
回复"复读机" / 一直重复 temperature 过低、无重复惩罚 temperature=0.9 + 开启重复惩罚 / presence_penalty
中文乱码 / 输出怪字 用了错误 vocab 文件 用模型自带的 vocab（如 rwkv_vocab_v20230424.txt）
回复过于简短/废话 模型偏小 + prompt 引导不足 调高 top_p、给更明确的指令、换更大模型
回答内容瞎编（幻觉） 所有 LLM 通病 关键事实走 RAG 检索约束
长对话后半段变笨 状态被挤压 / 上下文太长 分段总结、定期压缩状态、用 RAG 分担

采样参数速调口诀：要稳 → 低 temperature（0.2–0.5）；要创意 → 高 temperature（0.8–1.1）；要不重复 → 打开重复惩罚；要准确 → 配 RAG。

27.6 微调与状态类报错

症状 常见原因 解法
LoRA 微调 OOM batch 太大 / 序列太长 减小 batch_size、micro_bsz、ctx_len，或用 QLoRA
加载 .st 状态报维度不匹配 模型版本/规模不一致 状态文件和模型必须同版本同规模，重新导出
微调后变傻 / 灾难性遗忘 学习率太高 / 步数过多 降学习率（如 1e-5）、用 LoRA 而非全参、加正则
状态文件读取为空 序列化/路径问题 检查 pickle 文件完整性，确认读的是同一路径

State Tuning 的黄金法则：状态文件是"记忆快照"，换模型权重前先导出 .st；它只负责"性格/记忆"，不负责"知识"——知识靠权重或 RAG。
